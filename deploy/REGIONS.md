### 事实 2：**分片本身不会让"今天的视口查询"变快**——这次实测推翻了设计直觉

我原本的假设是"分片 ⇒ 索引更小 ⇒ 候选集更小 ⇒ 更快"。**实测把这个假设证伪了**，至少对当前的
`queryBbox` 路径是这样。逐条列实测（只读连接，3 次取中位数，见附录 B 的复现命令）：

| 查询步骤 | 生效缩放 | 实测耗时 | 耗时**与什么成正比** | 分片能帮上忙吗 |
| --- | --- | --- | --- | --- |
| POI 候选扫描（`idx_nodes_poi_low`，`_nodePoiPlan` 命中 z ≤ 15） | z10~z15 | z10 **7.3 ms** / z12 5.6 / z13 4.2 / z15 3.6 | **几乎什么都不成正比**——整个部分索引**全库只有 2,416 行** | **不能**。这条早就被优化过了，已经是零头 |
| 带标签节点扫描（`idx_nodes_tagged` 驱动） | 视口跨度 ≥ 0.3° | z10 **1,295 ms**（105,736 行） | 分片内**带标签节点总数** | 理论上能，**但默认配置下这条计划根本不会生效**（见下） |
| way 候选扫描（R*Tree 驱动） | z ≥ 13 | z13 **780 ms**（126,743 行）/ z16 30 ms（5,732 行） | **视口内 way 数** | **不能**，行都在视口里，跑不掉 |
| way 候选扫描（`idx_ways_lod_zoom` 驱动） | z ≤ 12 | z10 **176 ms**（23,616 行）/ z12 171 ms | 分片内 `lod_zoom ≤ zoom` 的行数（全库 z10 = 26,921 / z12 = 37,768） | **能**，但只有"视口不覆盖全片"时才真的省 |

**关键发现**：默认配置下 `idx_nodes_tagged` 那条计划**是死代码**。`_nodePoiPlan`（`server/osmdb.js`
快照 `438A4B4B0CAE` ≈第 **1893** 行）在 `zoom ≤ NODE_POI_INDEX_MAX_ZOOM(=15)` 时返回非空，于是
`queryBbox` 里的 `nodePlan ? <POI 索引 SQL> : <tagged/R*Tree SQL>`（同文件 ≈第 2250 行）
**永远走 POI 索引分支**；只有 z ≥ 16 才轮到 `_nodeScanHint`（≈第 1836 行），而 z16 的视口跨度
只有 0.033° < `NODE_SCAN_INDEX_SPAN(0.3)` → 走 `NOT INDEXED` → R*Tree 驱动。
所以那条 1,295 ms 是**反事实数字**，我在表里照样列出来，但它不代表现在的线上行为。

**因此：把今天的数据切成 N 片，视口查询的时间基本不动**（甚至因为扇出而略升）。
真正能从分区里拿到的东西是另外三项，见事实 3。

### 事实 3：**分区真正的收益在「启动 / 常驻内存 / 不让新城市拖慢老城市」**

- 现状（`server/index.js` 快照 `7355F6E8D3E2`）：`const rail = new RailGraph(db, {mode:'rail'})`
  第 **290** 行、`const road = new RailGraph(db, {mode:'bus'})` 第 **291** 行、
  `const population = new Population(db)` 第 **307** 行——三者的构造参数都是**同一个 db**，
  而 `RailGraph` 的取数语句是
  `` db.prepare(`SELECT id, tags FROM ways WHERE deleted = 0 AND tags LIKE '${like}'`) ``
  （`server/railgraph.js` 快照 `152D446B06FF` 第 **249** 行，`like` 在第 247 行 = `'%highway%'`
  或 `'%railway%'`）——**一次全库扫描**。`Population` 同理：
  `taggedWays: "SELECT id, tags FROM ways WHERE deleted=0 AND tags IS NOT NULL"`
  （`server/population.js` 快照 `4C66863C2BC9` 第 **590** 行）。
- 实测/文档化的代价（`server/index.js` 第 323~325 行的注释）：铁路网 ≈0.8 s、道路网 ≈**10~18 s**
  （91,873 条道路 / 107 万段 / 87 万节点）、人口网格首次是**分钟级整段同步循环**
  （第 553~558 行的注释）；稳态 RSS 0.55~0.85 GB（`deploy/DEPLOY.md:25`）。
- **加入天津 / 保定 / 张家口之后，这三项会按数据量线性变差。** 分区的价值就是把这个线性增长
  挡在门外：**只为激活区域建图**。

> **一句话总结这一节**：分区**不**是"让今天的北京更快"，而是"让北京 + 周边不变慢，同时把启动
> 与内存降下来"。所以 H2 的**基线必须是"同一个总数据集塞进一个库"**，而不是"今天的单城库"。
> 这个口径差别很关键，第 8 节把它写成了可执行的判据。

### 事实 4（必须提前知道）：分片**边际成本极低**，这是本设计能成立的根本原因

实测：在北京内部按 `lon = 116.391` 竖切一刀，**跨线的 way 只有 1,077 条（占 0.321%）**，
它们用到的不同节点 **18,823 个（占 0.863%）**；按 `lat = 39.966` 横切一刀，跨线 way 761 条
（0.227%）、涉及节点 20,279 个。北京与石家庄之间（`lon = 115.5`）**只有 3 条 way 跨过**——
两片之间本来就是空白带。

也就是说：**"跨片元素"在真实 OSM 数据里是极少数（千分之三）**，可以老老实实做复制 + 写穿透，
不需要设计一套复杂的分布式一致性。这是后面第 5 节敢给出确定性写入路由的底气。

### 事实 5：**`data/regions/beijing.sqlite` 是 `hebei.sqlite` 的严格子集**（实测）

这一条是**对"分片 bbox 天然大于行政范围"这个现象的实测**，它同时**推翻了**"相邻提取包会各自
截断边界要素、导致同 id 几何不同"的预期。以下全部为本次只读实测（两个真实分片库）：

| 检验项 | 实测结果 |
| --- | --- |
| `beijing` 的 nodes 是否都在 `hebei` 里 | **4,828,790 / 4,828,790 = 100%**，且 `lat`/`lon`/`version`/`deleted` **全部逐字段相同** |
| `beijing` 的 ways 是否都在 `hebei` 里 | **518,666 / 518,666 = 100%**，`version`/`node_count`/`length`/`tags`/4 个 bbox 列 **全部相同** |
| `beijing` 的 relations 是否都在 `hebei` 里 | **12,580 / 12,580 = 100%**，`member_count`/`version` 相同；**但 219 条的 bbox 不同** |
| 反向：仅 `beijing` 有的元素 | node **0** / way **0** / relation **0** ⇒ **严格子集** |
| `beijing` 的 `way_nodes` 引用能否在本片解析 | **0 缺失**（5,595,365 行全部可解析） |
| `hebei` 的 `way_nodes` 引用能否在本片解析 | **0 缺失**（17,549,272 行全部可解析） |
| 在天安门 z16 视口内两片的要素数 | node 京 24,984 = 冀 24,984；way 京 5,727 / 冀 5,728（**冀多恰好 1 条**） |
| 在天安门 z13 视口内 | node 京 691,876 = 冀 691,876；way 京 127,089 / 冀 127,090（**冀多恰好 1 条**） |

**三个必须记住的结论**：

1. **"跨片同 id 的 way 几何不同"这件事没有发生。** 我实测 518,666 条共有 way 的
   `version / node_count / length / tags / bbox` **全部相同**。原因很实在：提取包是**按 way 收录**的，
   一条 way 被选中就把它的**全部节点**一起带进来（实测两片 `way_nodes` 缺失都是 **0**），
   所以同一条 way 在两个包里拿到的是同一份完整节点列表，不存在"各自截断"。
   ⚠ **注意**：这与你在验收时会去查的假设相反，请以这两个库的实测为准。
2. **真正的差异只有两处**：
   - **关系的 bbox**：219/12,580（1.74%）不同，且**方向完全一致——河北的 bbox 219/219 全部完全包含北京的**。
     成因实测：`rel 912998（河北省）` 的 way 成员行两片都是 416 行，但**能解析出几何的**
     北京只有 **96** 条、河北 **416** 条；`rel 318110（长城）` 9,447 个成员行，
     可解析几何的北京 **540** / 河北 **2,090**。⇒ **关系 bbox 反映的是"该片手里有多少成员几何"，
     不是"要素真实范围"。它不可信，也不能跨片比较。**
   - **超长要素的收录差异**：那"多出来的 1 条 way"实测是 `way 626927231` =
     **「±800kV 锡林浩特-泰州」特高压输电线路**：**1,618 个节点、863,635 米（863 km）长**、
     bbox `lon 116.2473..118.1824 / lat 38.3505..44.2415`（**跨 6 个纬度**）。
     它在河北片里有完整 1,618 个节点（其中 278 个落北京声明框内），但**北京片整条都没有**。
3. **两片的 `data_bbox` 都被这类超长要素撑爆了**（实测）：

   | 分片 | `source_bounds`（提取包声明） | `data_bbox`（库内实际） | 溢出 |
   | --- | --- | --- | --- |
   | `beijing` | lat 39.4408~41.0638 / lon 115.4155~117.5095 | lat **35.1774**~41.3883 / lon **113.1691**~117.7519 | 南 **4.26°≈471 km**、西 2.25°≈191 km |
   | `hebei` | lat 36.0430~42.6249 / lon 113.4510~119.9982 | lat **33.1191**~44.2415 / lon **110.6494**~**126.6005** | 东 **6.60°**、西 2.80°、南 2.92°、北 1.62° |

   而**落在声明框外的节点其实极少**：`beijing` **6,686 个（0.138%）**、`hebei` **8,982 个（0.060%）**；
   way 是 `beijing` **79 条**（占 518,666 的 0.015%）、`hebei` **54 条**；relation 是 **38 / 39 条**。
   ⇒ **`data_bbox` 是"少数超长要素的极值"，用它做路由会把半个华北都算进来。**
   （`hebei` 的 `data_bbox` 比声明范围宽 **16° 经度**，而溢出的节点只有 8,982 个。）

   > **对你原话的两处修正**（以实测为准）：
   > ① 你说"超出声明范围的节点只有 6,686 个（0.138%）"——**数字完全正确**；
   > 但"那些远在河南（lat 35.18）的节点**全部无标签**"不成立：这 6,686 个框外节点里
   > **有 1,568 个（23%）带标签**，且按 1° 纬度带分布是 lat 39→3,801、lat 40→1,796、
   > lat 41→936、**lat 35→仅 153**。也就是说**大部分"溢出"其实是紧贴边界外沿的正常溢出**，
   > 真正跑到 471 km 外的只有 153 个节点。
   > ② "各自只被 1 条 way 引用"**基本正确**：6,655 个被 1 条引用、29 个被 2 条、2 个被 3 条。
   > 这个分布反而是好消息——**溢出节点几乎都是"某条长要素的孤立途经点"**，
   > 不会把大片稠密数据拖进别的分片。

### 事实 6：**两片的 id 分配器已经处在会碰撞的状态**（结论）

**`beijing` 与 `hebei` 的 `meta.next_relation_id` 逐位相同（21,408,528）**，`next_way_id` 只差 **6,677**，
`next_node_id` 只差 **89,382**。⇒ 两片各新建一条 relation，就会发出**同一个 id**。
这把原来的 **U13（"id 碰撞只是推理"）升级为"前置条件已实测"**，
id 分配方案从 §5.5 里的一条建议升级为 **§5.9 独立一节 + P2 的硬准入门槛**。
**完整数据、D 距离表、"已经发生过吗"的核查、方案选择、迁移步骤与可断言验收条件，全部见事实 8 与 §5.9。**

`data/regions/beijing.sqlite` 里除了 OSM 表，还完整带着

### 事实 8：**每个库一套 id 游标，两条序列迟早会正面撞上——而且已经撞到"只差 0 步"**

**代码事实（我逐行核过，与你的引用一致）**：

| 事实 | 位置（当前快照） |
| --- | --- |
| `class IdAllocator`：起始值取 `meta.next_*_id`，没有就取 `MAX(id)+1` | `server/dbschema.js` 第 **547~555** 行 |
| `alloc()`：取当前值 → `this.next[type]++` → **把新游标写回本库的 `meta`** | 同文件第 **557~561** 行（`setMeta(this.db, 'next_' + type + '_id', …)` 在第 559 行） |
| 一个库一个分配器 | `server/osmdb.js` ≈第 **1686** 行 `this.ids = new IdAllocator(this.db)` |
| 三个新建入口全用它 | `server/osmdb.js` ≈第 **3856 / 3884 / 3935** 行（`insertNode` / `insertWay` / `insertRelation`） |
| 导入器写 `next_*_id = 源文件最大 id + 余量`，注释明说"**这样 `next_*_id` 一定大于源文件里的任何 id（IdAllocator 靠它避免新建元素撞号）**" | `tools/import-osm.js` 第 **515 / 597 / 752~754** 行 |

**这个设计在单库下是对的**（一句话就能证明：游标 > 库里所有 id ⇒ 新号不可能撞到存量）。
**但它没有任何跨库语义**：每个库各写各的 `meta`，谁也不看谁。

**实测三个库的游标现状与"还要多久撞上"**：

| 库 | `next_node_id` | `next_way_id` | `next_relation_id` |
| --- | --- | --- | --- |
| `data/osm/osm.sqlite`（bj-1 候选） | 14,172,804,683 | 1,558,060,114 | 21,373,425 |
| `data/regions/beijing.sqlite` | 14,201,669,379 | 1,560,847,957 | **21,408,528** |
| `data/regions/hebei.sqlite` | 14,201,758,761 | 1,560,854,634 | **21,408,528** |

记 `D = |两库游标之差|`（单位 = "各新建多少次元素"）。两条递增序列一旦开始重叠，
**领先那条此后发出的每一个 id 都会与落后那条历史上发过的某个 id 完全相同**（不是"概率"，是恒等）：

| 片对 | `D(node)` | `D(way)` | `D(relation)` |
| --- | --- | --- | --- |
| `osm.sqlite` × `beijing.sqlite` | 28,864,696 | 2,787,843 | 35,103 |
| **`beijing.sqlite` × `hebei.sqlite`** | **89,382** | **6,677** | **0 ← 第一次新建就撞** |

⇒ **`beijing` 与 `hebei` 的 `next_relation_id` 逐位相同（都是 21,408,528）：两片各新建一条
relation，就会发出同一个 id。** 而 way 只要各新建 **6,677** 次就会进入"此后 100% 撞"的状态
——这个量级**在同一天内就能达到**（一次批量编辑 / 一个脚本 / 一次导入补数据都可能）。

**"已经发生过吗？"——我查了，这次没撞上，但差得非常近**：

- 玩家新建 node 的 id 落在石家庄真实 id 区间 `[244,083,053, 14,046,748,960]` 内的有 **1 个**；
- 该区间里有 110,766 个真实节点，单次命中概率约 **1/124,611**；
- **这 1 个没有撞上任何真实节点**（`JOIN hebei-only.nodes` 结果为 **0** 条，坐标无冲突）。

⇒ 合并石家庄时**没有丢数据**，但这是一次约 **1/125,000** 的逃过。而且这**不是**"风险很低"的意思：
上面那张 D 表说明，只要两片并存并被写入，撞号是**确定性事件**，只是"什么时候"的问题。

**⚠ 这件事为什么比"两个元素共用一个 id"更严重**（这是本节最重要的一句话）：

§4.2 的去重规则建立在一条隐含前提上：**"同 id ⇒ 同一要素"**（所以可以比 `version` 取新者）。
一旦撞号，两片里的**两个不同**要素会共用同一个 id，而合并器**看不出它与"边界重复要素"的区别**——
两者长得一模一样。于是 §4.2 的"取 `version` 大者"会**静默丢掉另一个要素**，
不报错、不崩溃、`truncation.complete` 还是 `true`。**这不是 §4.2 能防的，只能靠本节的身份分配来防。**

**⇒ 所以在 §0 就把两件事分清，后面全程分开写（这也是你第 4 点的要求）**：

| | **问题 A：边界重复 id** | **问题 B：新建元素撞号** |
| --- | --- | --- |
| 本质 | **同一个**要素出现在两片 | **两个不同**要素拿到同一个 id |
| 实测 | `beijing ⊂ hebei`，同 id 逐字段相同（0 处分歧） | 两片游标已经处于会撞的状态（`D(relation)=0`） |
| 检测方法 | 比 `version` / 几何指纹——**可检测** | **不可检测**（与 A 的外观完全相同） |
| 规则在哪 | **§4.2 规则 0 + §5.8**（去重、属主、镜像） | **§5.9**（id 区间划分） |
| 危害 | 带宽浪费、去重成本、账本虚高 | **静默丢数据、编辑/撤销/变更集指向错元素** |
| 关系 | A 是"读"的问题 | B 是"写"的问题；**B 一旦发生，A 的规则就会变成帮凶** |

## 1. 分片粒度与命名

### 1.1 两级模型：region（归属）× tile（存储）

| 层 | 单位 | 干什么用 | 是否影响寻址 |
| --- | --- | --- | --- |
| **region** | 城市 / 地级行政区（北京、廊坊、天津…） | 命名、**玩法归属**（"我的公司在哪座城"）、运维与文档口径 | 只是 tag，不参与查询寻址 |
| **tile** | 矩形分片（`data/regions/<id>.sqlite`） | **唯一**的物理单元：查询、写入、建图、卸载 | 参与寻址（bbox 相交） |

为什么不一件事用一个概念：

- 只用城市：北京一城就是全库的 **93.6% 节点 / 95.1% way**（实测：北京 bbox 内 2,043,160 节点 /
  319,649 way，全库 2,182,456 / 336,039），切成"一城一片"等于没切。
- 只用网格：玩家和运维说的都是"北京""廊坊"，没有 city 这一层，车站/线路/公告全都说不清归属。
- 两层分开之后，"先按城市上，将来某座城太大再切 tile"是**纯增量**动作，不动任何上层语义。

### 1.2 切法：**矩形 + 数据量平衡**（不是经纬网格、不是行政区多边形）

三个候选的取舍：

| 切法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **经纬度等距网格**（如 0.5°×0.5°） | 简单、可无限细分、bbox 判定 O(1) | 北京的数据**极度不均**：实测 0.5° 网格上 `39.5–40.0N / 116.0–116.5E` 一格就有 **1,129,106** 个节点、`116.5–117.0E` 一格 307,936，而 `38.5–39.5N / 114–116E` 整块是 **0** | ❌ 不用。均匀网格 = 一片撑死、一片空转 |
| **行政区多边形**（用 Geofabrik `.poly`） | 语义正确、玩家看得懂、和城市一一对应 | 判定要射线法；多边形凹凸严重（廊坊是围着北京的飞地状）；**跨区的 way 反而更多** | ⚠ 只用作 region 的 tag，不作 tile 的几何 |
| **矩形 + 数据量平衡切分**（本文推荐） | bbox 相交判定 O(1)；北京这种"中心极密 + 外围极疏"用它可以切出量级相近的片 | 片的形状与行政边界无关；切缝是数据驱动的、不直观 | ✅ **推荐**（见下方实测候选） |

**实测的候选切法**（本次在真实数据上按"带标签节点数"做递归 guillotine 中位数切分，
保证子矩形互不相交；用来切的密度代理是"带标签节点数"，因为那是 POI 下发的口径）：

```
北京（poly bbox 115.4155,39.4408 .. 117.5095,41.0638，共 105,712 个带标签节点）切 8 片：

  bj-1  115.415,39.441 .. 116.290,39.966   tagged 23,043 (21.8%)  面积约  4,319 km²
  bj-2  116.290,39.441 .. 116.391,39.966   tagged 20,645 (19.5%)  面积约    494 km²   ← 最密
  bj-3  115.415,39.966 .. 116.391,40.066   tagged 17,964 (17.0%)  面积约    917 km²
  bj-4  115.415,40.066 .. 116.391,41.064   tagged  5,881 ( 5.6%)  面积约  9,148 km²   ← 最疏（山区）
  bj-5  116.391,39.441 .. 116.540,39.916   tagged 13,604 (12.9%)  面积约    670 km²   ← 天安门在这片
  bj-6  116.540,39.441 .. 117.510,39.916   tagged  8,886 ( 8.4%)  面积约  4,327 km²
  bj-7  116.391,39.916 .. 117.510,40.016   tagged  9,548 ( 9.0%)  面积约  1,052 km²
  bj-8  116.391,40.016 .. 117.510,41.064   tagged  6,141 ( 5.8%)  面积约 11,025 km²   ← 最疏
```

> **注**：这 8 片的矩形**互不相交、并集 = 北京市界框**（这是它能用于 bbox 寻址的前提）。
> 我试过的另一种切法（先按经度排、再在子集里按纬度排）会得到 bbox 互相重叠的片，

## 2. 区域注册表

### 2.1 放哪里：`data/regions/registry.json`（机器可读 JSON），**不用数据库表**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **JSON 文件**（推荐） | 零依赖读写（项目零第三方依赖）；**可以用 `git diff` 审阅**；进程启动时一次读进内存 O(1) 查；运维改一行不用连库；坏了一眼能看出是哪一行 | 并发写不安全 | ✅ **推荐**。写入只由工具（导入器 / 运维脚本）做，服务端**只读** |
| SQLite 表（建在某个"主片"里） | 事务安全、可并发写 | **鸡生蛋**：要读注册表得先知道打开哪个库；主片损坏时整个集群失联；运维看不到明文 | ❌ |
| 放在 `config.json` | 与现有配置一致 | `config.json` 里已经有 `limits`/`transit` 两大块，塞进 8 个城市的 bbox/counts 会把它变成几百行；而且**注册表是数据（随导入变化），config 是行为（人写的）**，两者生命周期不同 | ❌ 混在一起会让人改错文件 |

> 顺带说明：项目已有 `tools/cities.json`（城市数据集注册表，`deploy/CITIES.md` 第 3 行说明它放在
> `tools/` 是因为 Dockerfile 只 `COPY tools/`）。**新注册表不要复用它**：`cities.json` 描述的是
> "下载哪个包 / 导进哪个孤立的库"（一城一库、切城即换存档），而 region 注册表描述的是
> "**同时**打开哪几片并合并"。语义不同，合并成一个文件会让"切城市"和"分区流式"两件事纠缠。
> 两者通过 `region.source` 字段引用同一个 URL 来保持一致。**注意**：`tools/` 在容器里有、
> `data/` 是数据卷（`.dockerignore` 排除 `data/`），所以注册表放 `data/regions/` 意味着
> **容器重建后要保证数据卷里有它**——这是部署要注意的一点（未验证：Docker 卷的持久化行为本次没测）。

### 2.2 字段定义

```jsonc
{
  "v": 1,
  "_note": "分片注册表。服务端只读；写入只由 tools/ 下的导入/裁切工具做。",
  "primary": "bj-1",              // 主片：玩法表与 owner 目录落在这里（见第 6 节）
  "builtAt": "2026-09-21T…Z",
  "sourceDb": "data/osm/osm.sqlite",   // 这批分片是从哪份库派生的（回滚线索）
  "sourceDbSha256": "…",               // 派生时的源库指纹（校验"分片是不是从这份库来的"）
  "idPlan": {                          // id 区间方案（见 §5.9；上线后不得更改）
    "node":     { "base": 10000000000000,    "band": 100000000 },
    "way":      { "base": 100000000000000,   "band": 100000000 },
    "relation": { "base": 1000000000000000,  "band": 100000000 },
    "maxShardIndex": 8191
  },
  "regions": {
    "bj-1": {
      "id": "bj-1",
      "region": "bj",                  // region 层 id（城市）
      "name": "北京",
```

**字段的取舍说明**：

- `bbox` **必须**与 `dataBbox` 分开。理由有实测依据：北京源包的**声明框**是
  116.08,39.68..116.77,40.18，而实测有 **137,872 个节点（6.32%）** 落在声明框之外
  （其中 110,766 个是后来合并进来的石家庄；扣掉它，**北京包自身仍溢出 27,106 个节点 ≈ 1.24%**——
  这是"跨边界的 way 把框外的节点一起带进来"的正常现象）。**寻址必须用 `bbox`（人定的、互不相交的
  矩形），`dataBbox` 只用来做健康自检**：如果 `dataBbox` 莫名比 `bbox` 大出几百公里，
  说明有关系把 bbox 撑爆了（见 R5）。
- `counts` 冗余写入注册表（库里 `meta.counts` 也有一份）：注册表是**启动时零成本**读的，
  而查 `meta.counts` 要为每个分片开一次连接。运维对比两者还能发现"分片被谁改过"。
- `sourceDbSha256`：第 11 节回滚时用得上——"这批分片是从哪份库、哪个时刻派生的"。
- **没有** `"writable": true/false` 这类字段：写入路由由第 5 节的规则决定，不由注册表开关决定。
  加一个开关就等于允许出现两套真相。

### 2.3 何时读、读几次

- `server/regiondb.js` 在**构造时读一次**，解析成内存结构（8 片 = 8 个对象，忽略不计）。
- 启动时做 **8 项自检**，任一项失败就**降级到单库模式**并打一条明确的 WARN（不让服务起不来）。
  **其中 6/7/8 三项是"问题 B（撞号）"的静态防线，纯只读、零成本，必须在 P0 就有**：
  1. 文件存在且可打开；
  2. `id` 与 `path.basename(file, '.sqlite')` **逐字相同**；
  3. `bbox` 合法（`minLon < maxLon && minLat < maxLat`，且在经纬度范围内）；
  4. **声明矩形两两不相交**（相交就对同一要素查询两次、合并时还要去重，是纯浪费且会造成
     重复计数进 `truncation`）。⚠ 实测 `beijing` × `hebei` 这一对**相交且内容还是包含关系** ⇒
     这一项会直接拦下它，这是**预期行为**，见 §5.8（应改建 `mirrorOf` 或重新裁片）；
  5. `primary` 指向一个存在的 id；
  6. **`shardIndex` 两两唯一，且都 ≤ `idPlan.maxShardIndex`**（§5.9.6 断言 1）；
  7. **每片的 `meta.id_base_*` 与 `shardIndex` 一致**（`id_base === base + shardIndex*band`），
     且 `meta.next_*_id ∈ [id_base, id_base + band)`（§5.9.6 断言 2）——
     **这一项抓的是"忘了把老游标重置成区间起点"（R51）**；
  8. **`MIN(idPlan.node.base) > 所有分片的 MAX(nodes.id)`**，way / relation 同理
     （§5.9.6 断言 3）——保证新 id 永不撞存量，**且不需要枚举存量**；
  9. `mirrorOf` 指向存在的 id，且**没有环**（A→B→A）；
  10. `contentSource` 相同的片之间若存在大量"同 id 不同 version"，报警（§11.1 的跨来源混用）。
- **不在运行时重读**。要改注册表就重启（或者将来加一个显式的 `POST /api/regions/reload`，
  但那需要管理员权限，属于后续工作）。

## 3. 视口 → 分片解析

### 3.1 目标与不变量

输入：`/api/map` 的 `bbox`（`server/index.js` 第 **1324** 行 `parseBbox`，已经是 `Number()` 且
夹到经纬度范围内、保证 `min < max`）。
输出：**有序的分片 id 列表**（顺序必须确定，因为它决定第 4 节的配额分配）。

三条不变量：

1. **不漏**：任何落在视口内的要素，其所属分片必须被选中。靠"分片 bbox 并集 ⊇ 该要素所在的
   几何范围"保证。**难点**是边界复制：一个 way 的节点可能落在邻片（见 5.3），所以
   **选中判据必须用 `bbox ∩ viewport ≠ ∅` 的宽松相交，而不是"要素中心在视口内"**。
2. **不重**：注册表矩形两两不相交（2.3 自检项 4），所以一个**几何上刚性的**要素只会被一个分片
   命中。但**复制的边界节点**会在两片同时出现 → 第 4.2 节的去重是必需的，不是可选的。
3. **确定性**：同一 `(bbox, zoom)` 永远得到同一个分片列表（顺序也相同）。这是"同一请求可复现"
   与第 8 节前后对照的前提。

### 3.2 判定：O(N) 扫描够不够？

**够，而且不该做索引。** 实测量级：试点 8 片。一次视口解析 = 8 次
`(r.minLon <= v.maxLon) && (r.maxLon >= v.minLon) && (r.minLat <= v.maxLat) && (r.maxLat >= v.minLat)`
——**十几次浮点比较，纳秒级**，而一次 `/api/map` 的 `queryBbox` 是 **200~1600 ms**（实测，
`logs/payload-baseline-fixed.json`：z13 957 ms、z10 1642 ms）。

> 所以任务书里担心的"每次请求扫所有分片元数据"**在这个规模下不是问题**，我为它做空间索引
> （把矩形塞进 R*Tree 或做四叉树）反而增加代码面与出 bug 的机会。**明确不做。**
> **但要立一条规矩**：分片数一旦超过 **64**（例如把北京切成 64 格），就必须改用"按经度分桶 +
> 桶内线性"或网格哈希，并把这条规矩写进代码注释——因为那时 64 次比较 × 每帧多次请求就不再是零头。
> **这条阈值 64 是估算，未实测。**

### 3.3 一级全局索引：要不要？

**要，但不是"索引结构"，而是"注册表本身就是一级全局索引"**：

- 注册表给出了**所有存在分片的完整列表 + 各自 bbox**——这就是一级全局索引的全部内容。
- 它解决的是"**哪些分片存在**"这个问题（不需要去 `glob` 目录、不需要试探着 `ATTACH`）。
- **不需要**额外的"要素 → 分片"倒排：那是第 5 节 `owner.sqlite` 的事，服务的是**写入**，
  不是视口查询。

**实现技术已实测可用**：`node:sqlite` 支持**只读 URI ATTACH**，且**跨库 R*Tree 查询可用**：

```
ATTACH DATABASE 'file:data/regions/sjz-1.sqlite?mode=ro' AS sjz1;
SELECT COUNT(*) FROM node_index WHERE max_lon>=? AND min_lon<=? AND max_lat>=? AND min_lat<=?;
```
本次实测：ATTACH 成功、`other.nodes` 可查（110,766 行）、跨库 R*Tree bbox 查询成功、
跨库子查询合并成功；对只读库执行 `CREATE TABLE` 被正确拒绝（`attempt to write a readonly database`）。

> **取舍**：ATTACH 让"一次 SQL 查多片"成为可能，看起来很诱人（不用在 JS 里合并）。
> **但我不推荐用它做主路径**，理由是：
> ① `queryBbox` 有 1,100+ 行、包含 LOD 分级、折线合并、关系成员裁剪、截断账本等**大量
> JS 侧逻辑**（`server/osmdb.js` 快照 `438A4B4B0CAE`：`queryBbox` 在 ≈**2051** 行，
> `truncation` 组装在 **2767** 行），这些逻辑**没办法**用一条跨库 SQL 表达；
> ② 每个分片都有一份自己的 `OsmDB`（要跑 `_auditSpatialIndexes`、`backfillWayLod`、`_prepare`
> 缓存预处理语句），ATTACH 会绕过这一切；
> ③ ATTACH 的连接数是有限制的（SQLite 默认 `SQLITE_MAX_ATTACHED = 10`），**8 片还行，
> 超过 10 片就挂**——这是个硬上限，会让"将来切更多片"变成一次架构返工。
> **结论**：主路径 = **每个分片一个 `OsmDB` 实例，JS 侧扇出 + 合并**；ATTACH 只留给
> 运维工具/自检脚本（那种场景只查 COUNT，正好合适）。

### 3.4 边界情况

| 情况 | 处理 | 理由 |
| --- | --- | --- |
| **视口只命中 1 片**（最高频：z ≥ 14 时几乎总是） | **直通**：不经过任何合并代码，直接把该片的 `OsmDB.queryBbox` 结果返回 | 这是 H2 的护城河：绝大多数请求走的是"在小库上跑今天的同一段代码"，**严格不劣于今天**（同一套计划，索引里的无关行更少） |
| **视口跨多片** | 扇出（见 4.1） | — |
| **视口极小**（z ≥ 19，视口 < 1 个 0.005° 格） | 仍然命中恰好 1 片（矩形互不相交 ⇒ 点必落一片） | 极小视口天然是单片的 |
| **视口覆盖全部片段** | 命中数 = N。**这是 H2 最危险的场景** | 见下方 `fanoutMax` |
| **视口完全在空白区**（例如两城之间） | 可能命中 2 片（各自 bbox 相交，但库里没要素）→ 两次查询各返回空 | 实测两片之间的空白带宽达 1°，`lon=115.5` 上只有 3 条 way 跨过。成本 = 2 次空查询（各 ~1 ms），可接受 |
| **视口跨到数据集之外** | 正常返回空，与今天行为一致 | — |
| **`bbox` 反了 / 非数字** | `parseBbox` 已返回 `null` → 400（`server/index.js:1324`）；分片层不再校验 | 不重复实现已有的校验 |

#### `fanoutMax`：把 H2 的风险摁死在这里

```jsonc
"regions": {
  "fanoutMax": 2,              // 命中分片数 > 这个值时，不走分片，回退单库
  "fallbackDb": "data/osm/osm.sqlite",
  "fallbackBelowZoom": 11      // 硬性：z < 这个值时一律回退单库（见下）
}
```

**为什么需要它**：z ≤ 12 的视口跨度实测是 2.115°(z10) / 1.057°(z11) / 0.529°(z12)——**会覆盖多个
分片**。此时扇出 N 次查询，总候选行数与单片相同还多出 N 份固定开销（开语句、R*Tree 定位、
JS 合并），**净结果是更慢**。这直接违反 H2。

**回退到单库为什么是"不变差"而不是"作弊"**：`data/osm/osm.sqlite` **本来就在**、本来就在被 8787
使用、而且它的低缩放路径今天已经调优过（`idx_ways_lod_zoom`、`idx_nodes_poi_low`、折线合并
`displayLines`、面合并 `displayAreas` 都是为低缩放做的）。用它在低缩放上兜底，
等于"**低缩放路径的性能与今天逐字节相同**"，H2 自动成立。

**代价（必须如实说）**：回退库必须保持"包含全部区域"——也就是**当周边城市加进来时，
回退库也要跟着变大**，否则低缩放会漏要素。两条路：
- (i) 回退库继续是"北京 + 石家庄"（今天的库），并把 `fallbackBelowZoom` 的**有效范围**
  限制在"只有 bj/sjz 有数据的区域"；视口涉及新城市时**不允许回退**，走分片扇出（可能变慢，
  但那是新增数据的代价，不是老数据的退化）。
- (ii) 定时把分片合并出一个小体积的"**低缩放概览库**"（只保留 `lod_zoom ≤ 13` 的 way +
  `idx_nodes_poi_low` 覆盖的节点 + 关系骨架）。实测这部分只有 **37,768 条 way**（`lod_zoom ≤ 12`，
  占全库 11.2%），体积会小一个数量级。
  ⚠ **但这条路有硬伤**：`detail=0/1`（客户端「完整 / 全部道路」档）在低缩放会关掉合并、
  要求全量 way（见 `queryBbox` 里 `coalescing` 的判据，`server/osmdb.js` ≈第 2086 行）。
  概览库满足不了那一档。**处理**：`detail ≤ 1 && zoom < throttle` 的请求**禁用回退**，
  强制走分片扇出并如实报 `truncation`。

> **推荐 (i) 起步**：不改任何数据，`fanoutMax=2` + `fallbackBelowZoom=11`，把风险关在门外；
> (ii) 留到实测证明低缩放确实被打疼之后再做。

### 3.5 取舍与风险

| # | 风险 | 影响 | 处理 |

| R9 | `fallbackBelowZoom` 掩盖了分片在低缩放的缺陷，**将来数据长大后回退库先炸**（它还在线性长大） | 中 | `/api/health` 回显回退库的 `sizeBytes` 与分片总数，做成一个可监控的数字；概览库方案 (ii) 是既定的下一步 |

### 3.6 两级内容判定：**声明矩形只做粗筛，逐要素判定一律用分片内的 R*Tree / 表列**

这一节回答"分片总 bbox 只是粗筛"这件事——**必须写成硬规则，否则两个方向都会出错**。

**硬规则（两条，缺一不可）**：

```
第一级（选片，粗筛）：
    候选分片 = { r ∈ 注册表 : r.bbox ∩ viewport ≠ ∅ }
    用的是【注册表里人定的、互斥的 bbox】，不是 data_bbox，也不是 source_bounds。

第二级（取要素，精判）：
    对每一个候选分片，各自跑 queryBbox 的**原生**逐要素判定 —— 
    nodes 走 node_index 的 R*Tree（或 idx_nodes_poi_low 的 lat/lon 列），
    ways 走 way_index 的 R*Tree（高缩放）或 ways 自己的 float64 bbox 列（低缩放的 lod 索引路径），
    relations 走 relation_index 的 R*Tree。
    ⇒ 这一级与"分片的总 bbox 有多大"完全无关。
```

**为什么必须是这两级，而不能只留一级**——两个反例都是实测出来的：

| 只留一级会怎样 | 实测反例 |
| --- | --- |
| **只用第一级（分片 bbox 相交就算内容命中）** | 会**多查**但不会漏。实测：`hebei` 的 `data_bbox` 是 `lon 110.65..126.60`（**16° 宽**），若拿它当判据，一个在天津的视口会把 `hebei` 选进来；反过来由于 `beijing ⊂ hebei`，**任何北京视口都会同时命中两片**，两片返回几乎完全相同的数据。浪费但不丢数据。 |
| **只用第二级（不设声明矩形，靠"哪片有数据就查哪片"）** | 会**漏**。因为"哪片有数据"必须先有一次查询才知道，而"要查哪些片"是查询的输入——循环依赖。而且实测存在**只存在于一片的超长要素**（`way 626927231`，863 km，只在北京…**只不在**北京片），若不按声明矩形选片就会漏掉它。 |
| **用 `data_bbox` 做第一级** | **最坏**：`beijing` 的 `data_bbox` 因为 153 个河南节点被拉到 `lat 35.18`；`hebei` 因为超长要素被拉到 `lon 126.60`。用它做第一级会让"北京视口必须扫河北全省 1,493 万节点"这类事情发生。**明令禁止**。 |

**另外两条与第一级配套的规则**：

1. **`source_bounds` 也不能当"内容边界"用**。实测：`beijing` 声明框外仍有 **6,686 个节点 (0.138%)**、
   **79 条 way**、**38 条 relation**；`hebei` 是 **8,982 个节点 (0.060%)**、**54 条 way**、**39 条 relation**。
   ⇒ `source_bounds` 只用于**健康自检**（"库里的东西是不是基本都在声明范围内"），
   用于**判断"这个请求该不该查这片"就是错的**——它会漏掉那 79 条跨界 way，
   而其中一条就是 863 km 的特高压线路。
2. **"分片 bbox 相交"不等于"该片真的有视口内的要素"**。所以扇出的结果必须允许"空返回"，
   并且**空的片也要如实出现在 `truncation.regions[]` 里**（标 `empty: true`），
   否则运维看不出"这个 bbox 实际打了几片、几片是空的"，第 8 节的扇出实测就没法做。

> **一句话**：`data_bbox` / `source_bounds` 是**健康指标**，`bbox`（注册表声明矩形）是**路由键**，
> R*Tree 是**内容判据**。三者混用是这一节要防的唯一错误。

## 4. 查询合并

### 4.1 总体做法：在 `osmdb.js` 的查询入口做，**不改载荷形状**

```
server/index.js  /api/map
        │  db.queryBbox({ ...bbox, zoom, ... })
        ▼
server/regiondb.js  RegionDB.queryBbox(opts)      ← 新模块，与 OsmDB 同形接口
        │  ① resolve(opts.bbox) → ['bj-1'] 或 ['bj-1','sjz-1']
        │  ② 单片：直接 return shard.queryBbox(opts)          ← 零开销直通
        │  ③ 多片：按 4.5 的配额依次调用 → merge()
        ▼
   同一份紧凑载荷对象（nodes/nodePack/ways/relations/displayLines/displayAreas/
   truncation/totals/zoom/viewOnly/enc）
        │
        ▼
server/index.js  照旧：payload.ms / payload.stats / payload.query → encodeBinaryPayload
        │
        ▼
客户端 World.unpackPayload → mergePayload            ← 一行都不改
```

**为什么必须在这里做**：

- 客户端 `World.mergePayload`（`public/js/world.js` 快照 `4CE13E24F395` 第 **2027** 行）
  与 `Render.completeness()` 依赖 `truncation` 的语义；客户端还有一整套"**拆块直到每块
  `truncation.complete === true`**"的协议（`public/js/mapdata.js` 第 1063 行 `_mapOnce` /
  第 1133 行 `_apply`，`detectCapped` → `_split`）。**只要服务端能对任何一块 bbox 给出
  诚实的 `complete`，客户端就完全不需要知道分片的存在。**
- BIN v1（`encodeBinaryPayload`）编的是**同一份对象**，几何段（`nodePack` / `coalesce` 折线 /
  视口面）原样搬运，`truncation` / `totals` / `zoom` 走 CORE 的 JSON 段（见 `server/osmdb.js`
  开头「二进制矢量载荷」的说明，≈第 1284 行：`| 1 | CORE | UTF-8 JSON：除几何以外的所有字段`）。
  所以**加一个 `truncation.regions` 是向后兼容的**（老客户端不认识就忽略）。
  ⚠ **但这需要实测确认**：`tests/bin-payload-test.js`（68 项）可能对 CORE 字段做了逐字段断言。

### 4.2 按 OSM id 去重：同 id 出现在两片怎么办（**问题 A**）

> **前提警告**：本节整节建立在一条隐含前提上——**"同 id ⇒ 同一要素"**。
> 这条前提**不是天然成立的**：如果分片之间会各自发出相同的 id（问题 B），
> 那么两个**不同**的要素会共用同一个 id，而本节"取 `version` 大者"的规则会**静默丢掉一个**，
> 且外观与"正常的边界重复"完全一样、无法区分。
> **⇒ 本节的规则只有在 §5.9 的 id 区间方案落地之后才成立。** 两件事分开看、分开验收。

**先说清楚为什么会出现**：边界复制的节点（第 5.4 节）+ 从两个提取包导入的同一元素。
后者有**实测证据**（三组）：`data/osm/hebei-only.sqlite`（源 `Shijiazhuang.osm.gz`）与
`data/osm/osm.sqlite`（合并后）**共同拥有全部 110,766 个 node id 与全部 16,037 个 way id**；
`data/regions/beijing.sqlite` × `hebei.sqlite` **共有全部 4,828,790 个 node id / 518,666 个 way id /
12,580 个 relation id**。今天一致，但**今天一致不代表明天一致**：只要一次编辑只落在一片，就分叉了
（第 5 节专治这个）。

去重规则（**确定性、可审计，且与"有哪些分片"无关**）：

**规则 0（新增，最重要）：先按 `version` 判，不按"哪片更全"判。**

```
对同一个 (type, id) 在 k 个分片里拿到的 k 行：
  1. 若所有行的 version 相同 → 内容必然相同（实测支持，见下）→ 取【属主片】那一行
  2. 若 version 不同 → 取 version 最大的那一行（并列则取 ts 大的；再并列取属主片）
     并且【必须报警】：truncation.regions[].conflicts + console.warn + /api/health 计数
  3. 若 version 相同但内容不同（几何指纹/标签/deleted 任一不同）
     → 这是【数据损坏】，不是正常分叉：取属主片那一行 + 报警 + 标 health 为 degraded
```

**为什么规则 0 的第 1 条可以放心"取谁都一样"——这次有了实测支撑**（两个真实分片）：

| 检验 | 实测 |
| --- | --- |
| 共有 way（518,666 条）里 `version` 不同的 | **0** |
| 共有 way 里 `node_count` / `length` / `tags` / 4 个 bbox 列任一不同的 | **0**（四项分别都是 0） |
| 共有 node（4,828,790 个）里 `lat`/`lon`/`version`/`deleted` 不同的 | **0**（四项分别都是 0） |
| 共有 relation（12,580 条）里 `member_count` / `version` 不同的 | **0** |

⇒ **"同 id 但几何不同"在两个真实的相邻提取包里没有发生。** 原因见事实 5 第 1 条：
提取包按 way 收录、节点全带（两片 `way_nodes` 缺失都是 0），所以同一条 way 拿到的是同一份完整节点表。
**但规则不能建立在"实测没发生"上**——所以规则 0 依然要求"version 相同才允许随便取"，并保留报警路径。

**逐条规则（覆盖你问的所有情况）**：

1. **键**：`(type, id)`。OSM id 全局唯一——实测三组证据：
   `hebei-only.sqlite` × `osm.sqlite` 共有全部 110,766 个 node id；
   `beijing.sqlite` × `hebei.sqlite` 共有全部 518,666 个 way id / 12,580 个 relation id / 4,828,790 个 node id。
2. **同版本**（`version` 相等）：**取属主片的那一行**。内容相同，取谁不影响画面，但**必须确定**，
   否则两次相同请求可能给出不同字节，破坏第 8 节的前后对照与 BIN 的逐字节可比性。
3. **版本不同 → 优先 `version` 大者，并且必须报警**（不许静默选择）：
   - 取 `(version, ts)` 较大的那一行用于本次响应（保证玩家看到较新的编辑，符合
     `mergePayload` 里"版本号只许往上走"的既有约定，`public/js/world.js` ≈第 2309 行）；
   - **同时**在 `truncation.regions[].conflicts` 里如实报出
     `[{type, id, shards:[...], versions:[...], ownerShard}]`；
   - 打 `console.warn`，`/api/health` 的 `regions.conflictCount` 加一；
   - **绝不**自动合并两边的标签/几何（那会造出 OSM 里不存在的第三个版本）；
   - **绝不**用"哪片数据更全"来决定（那会让结果依赖于"当时注册表里有哪些片"，
     违反"规则对所有分片一致"的要求）。
4. **一片 `deleted=1`、另一片 `deleted=0`**：同规则 0 按 `version` 判。软删除在
   `server/osmdb.js` 里是一等公民（`markNodeDeleted` ≈第 3874 行只置 `deleted=1` + 删 R*Tree 行），
   所以"删除"必须能跨片传播，否则被删的元素会从另一片"复活"。
   → 这是第 5 节写穿透必须处理的具体 case。
5. **`relations`：bbox 是唯一"同 id 却可能不同"的字段 —— 不许跨片比较，也不许当判据用。**
   实测：12,580 条共有 relation 里 **219 条 bbox 不同（1.74%）**，且**河北的 bbox 219/219 完全包含北京的**。
   成因是**成员几何的可得性不同**，不是数据不同：
   `rel 912998（河北省）` 两片都有 416 个 way 成员行，但能解析出几何的北京只有 **96**、河北 **416**；
   `rel 318110（长城）` 9,447 个成员行，可解析几何的北京 **540** / 河北 **2,090**。
   **规则**：
   - **不比较 relation 的 bbox**（它是派生量，不是真相）；
   - 关系**只由属主片提供**，成员集与裁剪账本（`relations[id][3]`、
     `cropped/memberTotal/memberKept/...`，`server/osmdb.js` ≈第 2038 行的格式说明）**直接取属主片的**，
     不从别片拼；
   - 关系"成员不全"**本来就不是分片引入的问题**——实测：`beijing` 缺 **129,891** 个 way 成员、
     `hebei` 缺 **164,800** 个（占它 640,390 个成员行的 **25.7%**）。任何单片都不全，
     所以正确做法是**如实记进裁剪账本**，而不是"试图拼全"。
6. **同步/镜像片的写规则**：见 §5.8（这是"另一个分片里那份副本怎么办"的答案）。

**去重的实现位置**：在 `merge()` 里、**在几何编码之前**。因为 `nodes` 会先被
`packNodesColumnar` 压成 `nodePack{ids,lat,lon}`（列式差分），一旦压完就不能再按 id 去重
（差分是连续的）。**顺序：按 id 合并字典 → 去重 → 各自打包。** 这是实现要点，写错了会很难查。

**去重的成本（实测可算）**：因为实测存在 `beijing ⊂ hebei` 这种**近乎完全重叠**的片对，
若路由不做处理，一个北京视口会返回两片**几乎逐字节相同**的数据：天安门 z16 是
way 5,727 + 5,728、node 24,984 + 24,984 ⇒ **去重前字节翻倍，去重后要做 5.7 万次 way / 2.5 万次 node 的判重**。
**这就是 §3.4 的 `fanoutMax` 与 §5.8 的"镜像片不上线"两条规则的必要性来源**——
不是性能优化，是**不这么做就会浪费一倍带宽**。


### 4.3 LOD / 合并（coalesce）/ 截断账本（`truncation`）在合并后怎么保持

各字段分四类处理（**这张表就是 `merge()` 的规格**）：

| 类别 | 字段 | 合并规则 | 理由 |
| --- | --- | --- | --- |
| **求和** | `truncation.lodFiltered` / `lodFilteredBy.*`、`kinds.ways.coalesced` 家族、`kinds.relations.member*`（`memberTotal/Returned/Cropped` 及按类型细分）、`lod.coalesce.ways/lines/paths/points/rawPoints`、`kinds.ways.neverSend*` | **各片相加** | 这些都是"条数账"，各片的要素集合互不相交（矩形不重叠），加上去就是全局真实值 |
| **与** | `truncation.complete`、`truncation.exact`、`kinds.*.complete`、`kinds.*.exact`、`truncation.cropComplete` | **`AND`**（任一片不完整 ⇒ 整体不完整） | 这是**证据**语义。`truncation.complete=true` 是客户端"不需要拆块"的唯一凭据（`server/osmdb.js` ≈第 2038 行的说明）。只要有一片没扫干净，整体就**不许**说完整——**宁可让客户端多拆一块，也绝不谎报完整** |
| **精确值上限** | `kinds.*.dropped`（扫干净时是精确值，被砍断时是 `null`） | 全部片都 `exact` ⇒ 相加；**只要有一片 `!exact` ⇒ `null``** | 沿用同一口径：数不出来就说数不出来 |
| **取第一个（属主片）** | `truncation.zoom`、`truncation.lod.*`（规则回显：`detail/source/minFillArea/roadSend/baseFloor/neverSend`）、`truncation.viewOnly`、`truncation.coalesce` 的**规则字段**（`minZoom/tolPx/coordDigits/minClassWays/budgetFrac/rule`）、`payload.viewOnly`、`payload.zoom`、`payload.enc` | 各片**必然相同**（同一份 config + 同一个 `opts` 推出来）；取第一片，并**断言相等**，不等就打 WARN | 它们描述的是"这次请求用了什么规则"，不是"数到了什么"，相加没有意义 |
| **新增** | `truncation.regions = [{id, hit, ms, features, complete, exact, skipped, conflicts?}]`、`totals.regions` | 新增字段 | 运维与实测需要它；老客户端忽略它；**不能**用它替代上面的任何字段 |

**`truncation.totals`（视口内候选总数）**：`totals.ways/nodes/relations` 是
"`candidates + unscanned`"（`server/osmdb.js` ≈第 2768 行），**各片相加**；
任一片的 `unscanned < 0`（未知）⇒ 该字段整体 `null`（沿用"不编数字"的口径）。

**折线合并（`displayLines`）/ 面合并（`displayAreas`）的语义**：

- `displayLines` 的条目**没有 way id**（只有几何），是给低缩放"只看不改"那一档用的
  （`coalescing` 判据在 `server/osmdb.js` ≈第 2086 行；`_coalesce` ≈第 3194 行）。
- **合并方式**：**各片各自合并，然后数组拼接**。
- **已知偏差（必须写进文档与验收）**：同一条样式类 + 同名字的折线如果跨了片缝，
  会被接成**两段**而不是一段，接缝处不做 `tolPx` 简化（`simplifyTrailMeters` 与接龙
  `chainWaysToTrails` 都是片内执行的）。**画面影响**：接缝处多一个线头，在 `tolPx`
  （默认几像素）量级，肉眼几乎不可见；**字节影响**：同一 bbox 下 `displayLines` 的
  `lines`/`paths` 计数会与单库不同 → **第 8 节的"逐字段相同"判据在低缩放要放宽为
  "要素 id 集合相同 + 几何 Hausdorff 距离 < tolPx"**，不能苛求逐字节。
- **账本**：`truncation.coalesce.ways/lines/paths/points/rawPoints` 相加；
  `byFamily` / `classes` 按 key 相加。`remainingWays`（预算没用完剩下的）**相加**。
- ⚠ **合并的预算**（`COALESCE_DEFAULTS.budget`）是**每片独立**算的（`budgetFrac` 在
  `coalesceOptsOf` 里 `0.05..1`）。多片时总预算 = N 倍单片预算 → 低缩放的 `displayLines`
  总量可能**超过今天的量**。**处理**：多片时按片数摊薄 `budget`（`budget / N`，下限 0.05），
  并把这个生效值写进 `truncation.coalesce.budgetFrac`（字段本来就回显）。**这一条未实测。**

### 4.4 `relations` 的特殊处理（长线关系）

实测：9,346 条有 bbox 的关系里，**41 条成员数 > 1000，合计 111,384 条成员行 = 全部成员行的 34%**
（`relation_members` 共 325,804 行）；1,200 条在 65~1000 之间。

- **关系不切分**：一条关系整体属于一个分片（属主片 = 其成员几何的代表点所在片，见 5.1）。
  `queryBbox` 里已经有一套成熟的**关系成员裁剪**（`relationCropPad` / `relationCropMinMembers`，
  `QUERY_CAPS` 在 `server/osmdb.js` 第 63 行；裁剪逻辑 ≈第 2328 行），
  它保证"请求框内的成员一条不少，框外的裁掉并如实记账"。
- **合并时 `relations` 字典直接取并集**（按 id，规则同 4.2），`relations[id][3]` 的裁剪账本
  取属主片的值。
- **`kinds.relations.member*` 相加**：各片的关系集合不相交，成员账可以相加。
- 一个**已知的、可接受的**偏差：如果视口跨两片，且某条长线关系横跨两片，它只在属主片被下发；
  另一片的视口内成员**不会**由这条关系带出来。但那些成员 way 本身如果落在视口内，
  会被那一片的 **way 扫描**独立下发（`kinds.relations.memberWays*` 的五分类账里
  `picked` 就是这一类，见 `server/osmdb.js` 第 2722~2727 行）。**画面不少东西**，
  但 `memberWays*` 的账在跨片时会与单库不同 → 写进第 8 节的放宽项。
  **未实测**，需要在 `bj|sjz` 两片 + 一条跨片测试关系上验证。

### 4.5 合并后的要素数上限与配额

现状：`limits.viewportLimit = 15000`（`config.json:21`），候选上限 = `limit × wayCandidates(12)`
/ `× nodeCandidates(8)`，关系上限 `relationLimit = 10000`（`server/osmdb.js` 第 63 行 `QUERY_CAPS`）。

三个候选方案：

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **按比例分配** | 每片配额 = `limit × (该片权重 / 总权重)` | 公平、可预测 | 小片会拿到个位数的配额，**配额没用完就返回**，而大片可能被卡住 → 总下发量反而更少、`complete=false` 更频繁，客户端拆块更多 | ❌ |
| **先到先得（固定顺序）** | 按注册表 id 排序，依次拿 `min(剩余额度, 该片候选)`；额度用尽后剩下的片**标 `skipped:'budget'`** | 实现最简单；配额一定用满；顺序确定 → 可复现 | 排序靠后的片在繁忙视口下总是被饿死（低缩放的 `bj-1` 会永远吃掉全部额度） | ⚠ 可用，但要配合下面的修正 |
| **每片各自完整 + 总额封顶**（推荐） | 每片按**自己的** `limit` 扫（默认 15000）→ 各片都 `complete`；合并后如果总数 > `limit`，**如实置 `truncated=true`** 并让**客户端按既有协议拆块** | 每片的完整性可独立证明；客户端协议零改动；拆分后每块 bbox 更小 → 命中更少片 → 最终收敛 | 单次响应的字节数最多到 N × 今天的量 | ✅ **推荐**，配一条硬上限 |

**推荐的完整规则**：

```
1. 每片用 opts 原样调用（limit 不变）→ 每片有自己的 truncation（诚实、独立）
2. 合并。若合并后 (ways + nodes + relations) 总数 > limit：
     truncation.complete = false（客户端会拆块）
     truncation.regions[i].overQuota = true
3. 硬上限 mergedBytesLimit（新增 config，默认 4 MB）：
     合并过程中累加"估算字节数"（各片 payload 的对象计数 × 经验系数，或直接用各片
     JSON 长度），超限就停止追加后续分片，并把剩下的片标 skipped:'bytes'
     —— 这保证"一次响应不会大到把手机端打死"
4. 顺序 = 注册表 id 升序（确定性）。粒度更细的策略（按视口重叠面积排序）留到实测
   证明"顺序明显影响体验"之后再做。
```

**为什么不用"先跑一片，看它够不够再决定要不要跑别的"**：那会让响应的**内容取决于时序**，
不可复现（违反 3.1 的不变量 3），而且第 8 节的前后对照就没法做了。
**固定顺序 + 硬上限 = 可复现且可解释。**

### 4.6 实现要点清单（写代码时照这个做）

## 5. 写入路由（最要紧的一环）

### 5.1 术语与不变量

- **属主片（home shard）**：一个元素**唯一**的权威存储位置。**写只写属主片。**
- **副本片（replica shard）**：为了几何完整性而在别的片里保存的**节点副本**（不是 way/relation 副本）。
  副本**只读、且必须跟随属主更新**。

**核心不变量（要断言、要自检、要能报错）**：

> **I1**：每个 `(type, id)` 恰好有一个属主片。
> **I2**：副本只允许存在于 `nodes` 表，且副本节点的 `(lat, lon, version, deleted, tags)`
> 必须与属主**逐字段相同**。
> **I3**：`ways`/`relations` **绝不复制**。

为什么 way/relation 不许复制：`updateNode` 会通过 `wayRefsForNode`
（`server/osmdb.js` ≈第 3870 行 `SELECT DISTINCT way_id FROM way_nodes WHERE node_id = ?`）
**反查并重算所有引用它的 way 的 bbox**。如果一条 way 在两片各有一份，改一个节点就要重算两份，
而且 `recomputeRelationsOfWay`（`server/osmdb.js` ≈第 3999 行）还会牵动关系 —— 复制 way
= 把一个 O(引用数) 的操作变成跨库分布式写，必然分叉。**实测支持这个决定**：
跨片缝的 way 只占 **0.32%**，所以"way 属于哪片"这个问题的规模本来就很小。

### 5.2 属主判定（确定性规则）

```
homeOf(type, id, geom):
  ① 取代表点（representative point）：
     node     → (lat, lon)
     way      → 第 floor(len/2) 个节点的坐标（长为 0 时取第一个）
     relation → 递归取"第一个能解析出几何的成员的几何中心"，深度上限 4；
                解析不出（成员缺失 / 全是被删元素）→ 落到 primary 片
  ② 把坐标吸附到固定网格：round(coord * 1e7) / 1e7（≈1.1 cm）
     —— 保证边界上的点判定稳定，不受浮点尾数影响
  ③ 在注册表 bbox 里找"包含该点"的片（半开区间 [min, max)，避免邻接边界二义）
  ④ 落在两片（不该发生，因为矩形不相交）→ 取 id 字典序最小的那一片，并打 WARN
  ⑤ 不在任何片内（数据比声明框大——实测北京包自身溢出 1.24%）→ 取 primary 片，并打 WARN
```

**为什么 way 用"中间节点"而不是"bbox 中心"**：

- bbox 中心可能**根本不在 way 上**（L 形、U 形、环形道路），也**可能落在另一片**；
- 更糟的是：bbox 中心会**随着编辑而漂**（拉长一条边就变），而中间节点通常不变 ——
  我们希望"属主"在几何微调时**尽量稳定**，否则每次编辑都可能触发元素搬家。
- 用中间节点还有一个决定性的好处：**它能直接复用 OSM 提取包的既有约定**（extract 以
  way 为粒度收录，节点跟着 way 走），所以"派生的分片"和"重新下载的提取包"结果一致。

**取舍：属主一次性冻结 vs 每次重算**

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 每次按几何重算 | 无状态、不需要目录 | **编辑会让元素搬家** → 搬家要不分叉就必须跨库搬数据；而且"搬家"本身需要分布式事务 |
| **一次性冻结 + 目录**（推荐） | 写入 O(1)；搬家是**显式操作**、可审计、可以拒绝 | 需要一个 `owner.sqlite` 目录；几何漂移到别的片后该片会"多存一份框外的数据"（**这没问题**——实测 OSM 提取包本来就有 1.24% 的框外节点） |

**结论：属主在导入/新建时确定一次，之后冻结。** 编辑**永远不搬家**。

### 5.3 `owner.sqlite`：属主目录

```sql
-- data/regions/owner.sqlite（独立小库，不放在任何分片里）
CREATE TABLE IF NOT EXISTS owner(
  kind  INTEGER NOT NULL,       -- 0=node 1=way 2=relation
  id    INTEGER NOT NULL,
  shard TEXT    NOT NULL,       -- 分片 id，如 'bj-1'
  since INTEGER NOT NULL,       -- 归属确定时间（ms）
  PRIMARY KEY(kind, id)
) WITHOUT ROWID;

-- 副本表：只对"边界节点"建行（见 5.4）
CREATE TABLE IF NOT EXISTS refs(
  node_id INTEGER NOT NULL,
  shard   TEXT    NOT NULL,     -- 保存了这个节点副本的片
  PRIMARY KEY(node_id, shard)
) WITHOUT ROWID;

-- id 区间台账（见 §5.9）：**只作审计用，不参与发号**
--   ★ 这里【没有】全局计数器：发号不需要协调（§5.9.2 选了方案 A）。
--   这张表的唯一用途是让 --regions-audit 不打开分片也能核对"区间两两不相交"。
CREATE TABLE IF NOT EXISTS idband(
  shard      TEXT    PRIMARY KEY,
  shard_index INTEGER NOT NULL UNIQUE,   -- UNIQUE 就是"区间不相交"的结构保证
  base_node  INTEGER NOT NULL,
  base_way   INTEGER NOT NULL,
  base_rel   INTEGER NOT NULL,
  band       INTEGER NOT NULL,
  assigned_at INTEGER NOT NULL
);
```

> ⚠ **本文早期版本在 §5.3/§5.5 推荐过"把发号上收成一个全局 `idseq` 计数器"。那个方案已被
> §5.9 取代**：全局计数器引入单点、且每次新建多一次跨库写；而 **§5.9 的固定区间方案零协调、
> 零额外 IO、且可以纯静态断言**。`idseq` 表**不要建**；`idband` 只是审计台账。
> 上表里的 `shard_index UNIQUE` 不是装饰——它让"两片区间重合"在 SQLite 层面就无法写入。

**规模估算（估算，非实测）**：今天 2,182,456 nodes + 336,039 ways + 10,309 relations ≈ **2.53M 行**，
`WITHOUT ROWID` 的 (kind,id)→shard 大约 **20~25 B/行** ⇒ **约 50~65 MB**。
8 城试点若总元素量到 10M ⇒ **约 200~260 MB**，仍可接受。
（优化空间：由于属主是"按矩形 + 中间节点"决定的，`id` 在每片里往往是**成段连续**的，
可以用 `(kind, shard, id_lo, id_hi)` 的区间表压缩到几千行；但**不要一开始就做这个优化** ——
区间表在"元素搬家 / 新建元素 id 散布"之后会碎掉，复杂度换不来多少收益。**这一条是设计判断，未实测。**）

**读取**：`owner.sqlite` 常驻打开（一个连接），写用 `BEGIN IMMEDIATE`。
`owner` 是**权威**：写路由只查它，不试探分片。这也是 3.3 里说"倒排索引服务写入、不服务查询"的意思。

### 5.4 跨片元素：只复制节点，且写穿透

**问题**：一条 way 横跨 `bj-1` 与 `bj-3`（实测这种 way 占 0.32%）。way 只能住一片，
但它的节点里有一部分在另一片。`recomputeWayGeometry` 需要节点坐标
（`_st.wayNodeIds` → 从 `nodes` 读，`server/osmdb.js` ≈第 3969 行的 `recomputeWayGeometry`），
`_fetchNodes`（≈第 3704 行）下发几何时也要坐标。**节点不在本片 ⇒ way 没几何 ⇒ 画面静默缺东西。**

**方案：只复制节点，写穿透。**

```
建片时（一次性）：
  对每条跨缝 way W（home = A）：
    对 W 的每个节点 N：
      若 N ∉ A：在 A 里插入 N 的完整副本（lat/lon/version/tags/deleted/ts）
                写 refs(N, A)

运行时（节点被编辑）：
  updateNode(id, ...) 落在 owner(id) 片 A：
    ① A 更新 nodes / node_index（照旧）
    ② 查 refs WHERE node_id = id → [A, B, C…]
    ③ 对每个 B ≠ A：把同样的行写进 B 的 nodes / node_index
       （同一条 SQL，只是换了连接；失败就记 WARN 并入重试队列 —— 
        副本短暂不一致只会让画面在接缝处旧一帧，不会丢数据）
    ④ 如果 deleted 从 0→1：副本片也要置 deleted=1 并删 R*Tree 行
       （否则被删的节点会在另一片"复活" —— 见 4.2 第 4 条）
```

**实测的规模（这是这个方案可行的关键）**：竖切一刀涉及 **18,823 个节点**、横切一刀 **20,279 个节点**
（分别占全库 0.86% / 0.93%）。8 片最多 7 条缝 ⇒ 上界约 13 万个副本行（**估算**，因为一条缝上的
节点可能被多条缝共享，实际更少）。**这个量级下，"写穿透"就是几条 UPDATE，完全不需要分布式事务。**

**取舍**：

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 复制节点 + 写穿透（推荐） | 几何完整；改动面小；量级只有 0.9% | 需要 `refs` 表；需要跨库写（非原子） | ✅ |
| way 不跨片（把跨缝 way 硬切两半） | 无副本 | **改了 OSM 语义**（会多出两个 way、关系成员断裂、玩家看到 id 变了）；实测 1,077 条 way 会受影响 | ❌ 绝对不做 |
| 内联几何（way 自带坐标 blob） | 不需要副本 | `queryBbox` 的几何路径全建立在 `way_nodes` + `nodes` 上（`wayNodesBatch` ≈第 3677 行、`_fetchNodes` ≈第 3704 行），内联等于重写几何层；而且 `updateNode` 的 way 反查会失效 | ❌ |
| 只允许 way 的节点全在属主片 | 零副本 | 等于禁止跨边界编辑（玩家一过界就报错） | ❌ |

### 5.5 新建元素的路由

编辑器新建元素时（`OsmOps._createNode` / `_createWay` / `_createRelation`，
`server/osmops.js` 快照 `F9993258FFC9` 第 850 / 1017 / 1296 行）：

```
1. 新建 node：有坐标 → home = homeOf('node', id, {lat, lon})
2. 新建 way：先解析几何（`_resolveWayGeometry`，`osmops.js` ≈第 971 行会按需创建节点）
   → 节点已经各有属主；way 的 home = homeOf('way', id, 第 floor(n/2) 个节点的坐标)
   → 若 way 的某些节点不在 home 片：在 home 片插入这些节点的**副本** + 写 refs
3. 新建 relation：成员通常是已有的 way/node
   → home = 第一个可解析成员的代表点所在片；解析不出 → primary
4. id 分配：**必须全局唯一**（见 §5.9 —— 这是**独立的第 9 节**，规则不与本节混写）
```

**id 分配是这里最容易被忽略的坑，而且有实测风险证据**：

- 现状 `IdAllocator`（`server/dbschema.js` 快照 `5229C12D8193` 第 **547~561** 行）用库自己的
  `meta.next_node_id / next_way_id / next_relation_id`，初始化时
  `Number(getMeta(db,'next_node_id',0)) || (SELECT MAX(id)+1 FROM nodes)`；
  `OsmDB` 一个库一个（`osmdb.js` ≈1686 行）。
- 实测三个库的游标：`osm.sqlite` 14,172,804,683 / `beijing.sqlite` 14,201,669,379 /
  `hebei.sqlite` 14,201,758,761（node）；**`beijing` 与 `hebei` 的 `next_relation_id`
  逐位相同（21,408,528）**，`next_way_id` 只差 **6,677**。
- **处理**：见 **§5.9**。一句话：**给每片一组固定的、互不相交的 id 区间**，
  方案 (A)，不引入任何跨库协调。**这是 P2 的硬准入门槛。**
  （本文早期版本曾建议"上收成全局计数器"，已按 §5.9.3 的取舍分析**否决**——
  那会引入单点，而且 §5.9 的实测证据表明固定区间就够、还更好断言。）

### 5.6 怎么避免"同一个元素被两片各写一份导致数据分叉"（总结）

五道闸门，缺一不可：

1. **属主唯一**：`owner.sqlite` 的 `PRIMARY KEY(kind,id)` 从结构上保证 I1。
2. **写入口唯一**：`OsmOps` / `Transit` 拿到的 `db` 是 `RegionDB`，它的写方法
   （`insertNode/updateNode/markNodeDeleted/insertWay/updateWayGeometry/updateWayTags/
   markWayDeleted/insertRelation/updateRelation/markRelationDeleted/recomputeWayGeometry/
   …，`server/osmdb.js` ≈第 3855~4001 行一带共 12 个）**内部先查 owner 再路由**；
   业务层（`osmops.js`）**一行都不改**。这是"改动面最小 + 不可绕过"的最好组合。
3. **way/relation 不复制**（I3），所以没有"两片各有一份 way"这种状态存在。
4. **节点副本写穿透 + 删除传播**（5.4），保证 I2；副本上的几何偏移在接缝处，
   且 `refs` 让"谁有副本"是**可枚举**的（不是靠猜）。
5. **分叉检测**：`owner.sqlite` 有权威属主 ⇒ 如果某片出现了不属于自己的 `(type,id)`，
   那就是分叉。启动自检 + 每次 `RegionDB` 打开分片时抽样核对；
   第 4.2 第 3 条在查询期也能发现分叉并如实上报 `conflicts`。
   → 加一个运维命令 `node server/index.js --regions-audit`（与现有 `--graph-selfcheck`
   同风格，`server/index.js` ≈第 2219 行有现成的骨架可参照）打印：
   每片的元素数、与 owner 不一致的行数、副本一致性抽样、id 分配器当前值。

| H2 | 写入是低频操作，路由多一次 owner 查询（单表主键，微秒级） | — | 无影响 |

### 5.8 重叠片（mirror）：**属主 = 最全的那一片；镜像片不参与读，也不接受写**

这一节回答"**跨片同 id 的元素，玩家编辑时写到哪个分片、另一个分片里那份副本怎么办**"。
§5.1~5.6 假设的是"一个元素只有一个属主、副本只允许是 `nodes`"；**当两片本来就含同一个元素时
（实测 `beijing ⊂ hebei` 就是这个情况），必须有额外的规则**，否则会出现两种坏结果：
写一片、另一片永远停在旧版本（玩家在北京改、从河北看是老版本），或者两边都写（分叉）。

#### 5.8.1 三个概念要分清

| 概念 | 定义 | 实测例子 |
| --- | --- | --- |
| **重叠片（overlap）** | 两片的注册表 bbox 相交，且库里存在相同 `(type,id)` 的元素 | `beijing` × `hebei`：**100% 重叠**（严格子集） |
| **镜像片（mirror）** | 重叠片里**内容被另一片完全包含**的那一片 | `beijing`（0 个元素是"仅它有的"） |
| **属主片（owner）** | 唯一权威的存储位置，**写只写这里** | 由 §5.2 的 `homeOf` 决定，**且必须在 `owner.sqlite` 里冻结** |

#### 5.8.2 规则（四条，前两条是硬要求）

**规则 A（读）：镜像片默认不参与路由。**
注册表给每片一个可选字段，指向"覆盖它的那一片"：

```jsonc
"beijing": { ..., "mirrorOf": "hebei" }   // 北京片的内容是河北片的子集 ⇒ 标为镜像
```

`regiondb.resolve(bbox)` 在选片时**先把镜像片剔掉**。理由（实测）：不剔的话，
一个天安门 z16 视口会同时命中两片，返回 **way 5,727 + 5,728 / node 24,984 + 24,984
——几乎逐字节重复**，带宽白翻一倍、还要做 5.7 万次 way + 2.5 万次 node 的去重。
剔掉之后"北京视口"只查 `hebei` 一片 ⇒ **单片直通**，H2 直接受益。

**规则 B（写）：属主 = 覆盖链上"最全"的那一片；写只写属主片，镜像片的那份不做同步——因为它根本不会再被读到。**
这是"另一个分片里的副本怎么办"的答案：**不办**。因为规则 A 已经让镜像片退出读路径，
它里面的那份副本既不参与渲染也不参与查询，**它的新鲜度没有任何消费者**。
于是：

- **不需要写穿透到镜像片**（省掉 §5.4 那套跨库写，代价是镜像片的数据会变陈旧，但无人读）；
- **不需要删除镜像片里的副本**（实测它占 948 MB，删数据是不可逆动作，见 §11.1 的原则）；
- **必须做的是**：启动自检 + `--regions-audit` **核对"镜像片仍然被覆盖"**。
  一旦检测到镜像片里出现了"覆盖片没有的元素"（说明包含关系不再成立），
  **立刻把该片的 `mirrorOf` 作废并降级为正常片**（重新参与路由），同时打 ERROR。
  这是一个**单调可检测**的条件（`SELECT COUNT(*) FROM mirror WHERE NOT EXISTS(...覆盖片...)`），
  实测当前是 **0**，代价是每次审计一次全表 anti-join（实测 4.8M × 14.9M 的 anti-join
  在这个规模上可接受——本次跑的 `NOT EXISTS` 查询是秒级的）。

**规则 C（写）：属主判定仍然走 §5.2 的 `homeOf`，但 `homeOf` 必须"在覆盖链上取最全片"。**
具体：若 `homeOf` 算出的片 P 有 `mirrorOf: Q`，则属主**上溯到 Q**（可能多级）。
实测后果：北京城区的元素，属主从 `beijing` 变成 `hebei`。这与"北京片下线"是一致的。

**规则 D（边界要素的写）：仍然按 §5.4 复制节点、写穿透，但"哪些片需要副本"要先过滤掉镜像片。**
即 `refs` 表里**不登记镜像片**。

#### 5.8.3 取舍：为什么不做"两边都写"

| 方案 | 好处 | 代价 | 结论 |
| --- | --- | --- | --- |
| **镜像片退出读 + 写只写覆盖片**（推荐） | 实现最小；镜像片陈旧无害；带宽不翻倍 | 镜像片的数据会与覆盖片分叉（但无人读） | ✅ |
| 写穿透到镜像片（两片同时更新） | 两边都新鲜 | 每次编辑两倍写 + 两倍失败面；镜像片本来就不该被读，属于"为没人看的数据付钱" | ❌ |
| 路由时按"哪片更全"动态选片 | 不需要注册表配置 | **结果依赖当时的注册表内容 ⇒ 违反 §4.2"规则对所有分片一致"**；且"更全"要现算，无法在选片阶段知道 | ❌ |
| 删掉镜像片 | 干净 | 不可逆；实测北京片有 948 MB 且 §11.1 的原则是"原库只读、回滚靠指回去" | ❌ 除非用户明确要求 |

#### 5.8.4 ⚠ **必须提醒的一件运维决策**（不写代码，但会决定试点成败）

实测 **`beijing` 是 `hebei` 的严格子集**，所以按规则 A/B 上线时 **`beijing` 片会完全不参与服务**，
"分区流式"在试点里就只剩**一片 14,922,355 节点 / 1,560,629 way 的河北片**——
这等于把全部数据塞进一个大库，**§7 的"按区域惰性建图"与 §8 的启动/内存收益全部落空**
（河北片的两项"分片越小越省"的索引实测是：POI 索引 **73,820 行**、`lod_zoom ≤ 10` 的 way **162,118 条**，
分别是北京片 8,868 / 36,627 的 **8.3 倍 / 4.4 倍**）。

**所以要真正拿到收益，必须做下面任一件**（按推荐排序）：

1. **把 `hebei.sqlite` 当原料库，裁成真正互斥的市级片**（北京 / 廊坊 / 天津 / 保定 / 石家庄 / 唐山 / …）。
   需要一个"按 bbox 或多边形裁库"的新工具（目前不存在，§11.2 列了它必须处理的 6 个坑）。
   裁片的**互斥性由人定的声明矩形保证**，而**不要求两片的内容不相交**——
   这与 §3.6 的两级判定是自洽的：**声明矩形互斥即可路由，内容重叠由 §4.2 去重 + §5.8 属主规则处理**。
2. 或者**用 `tools/fetch-overpass.js --bbox` 直接抓每个城市的矩形框**（工具已存在），
   抓出来的片天然互斥（只要 bbox 不重叠），缺点是 Overpass 的关系会不全
   （`tools/fetch-overpass.js:22` 的注释明说了这一点）。
3. 或者**接受"一片河北"的试点**，但把目标从"更快的视口查询"改成"验证分片机制本身"
   （注册表 / 寻址 / 合并 / 写入路由 / 去重），并**明确写下"性能收益要等裁片之后才有"**。

> **我的推荐是 1，并且第 1 步就做 P0**：把 `hebei.sqlite` 裁出 `bj` / `lf` / `tj` 三片
> （实测这三片覆盖用户要的"北京 + 周边"核心，且互斥），`hebei.sqlite` 留作原料与回退。
> 在此之前，**不要**把 `hebei` + `beijing` 这一对按"两片"上线——那只会得到"重复一倍带宽
> + 一个 14.9M 节点的巨片"。

### 5.9 新元素 id 的分配（**问题 B**：分片之间撞号）——必须与 §4.2/§5.8 分开看

> 先把两件事钉死：**§4.2 规则 0 与 §5.8 处理的是"同一个要素出现在两片"（问题 A）**；
> **本节处理的是"两个不同要素拿到同一个 id"（问题 B）**。两者外观完全相同、危害完全不同，
> 处理规则也完全不同（见 §0 事实 8 末尾的对照表）。**不要把它们的规则混写。**

#### 5.9.1 为什么必须做，以及为什么 §4.2 挡不住

实测（§0 事实 8）：`data/regions/beijing.sqlite` 与 `hebei.sqlite` 的 `next_relation_id`
**逐位相同（21,408,528）**；`next_way_id` 只差 **6,677**（各新建 6,677 次 way 之后，
领先那条发出的每个 id 都与落后那条历史上的某个 id **完全相同**）。

而 `IdAllocator` 是**纯库内状态**（`dbschema.js:547~561`：读本库 `meta` → `++` → 写回本库 `meta`），
`OsmDB` 里一个库一个（`osmdb.js:1686`），三个新建入口全走它
（`osmdb.js:3856/3884/3935`）——**它没有任何跨库协调，也没有"我属于哪一片"的概念**。

**关键**：撞号之后，两片里的两个不同要素共用同一个 id，合并器**无法把它与问题 A 区分开**，
于是 §4.2 的"取 `version` 大者"会静默丢掉一个要素。**所以 §5.9 是 §4.2 的前提，
不是它的补充。**

#### 5.9.2 方案选择：**(A) 按分片划分 id 区间**（推荐）

三个候选逐一评估：

| 方案 | 做法 | 正确性 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| **(A) 分片独占 id 区间** | 每片有一组互不相交的 `[base, base+band)`；`IdAllocator` 从本片区间的 `base` 起算；**零协调、确定性、可断言** | ✅ 从构造上保证"任意两片发出的 id 不相等" | 需要给 `IdAllocator` 加一个上界断言（十几行）；导入器/注册表要带 `shardIndex` | ✅ **推荐** |
| **(B) 全局 id 计数器库** | 一个小 SQLite（如 `owner.sqlite`）存全局 `idseq`，所有分片向它取号 | ✅ 正确 | ❌ 引入**单点**：那个库丢了/锁住了，**所有分片都不能新建元素**；每次新建多一次跨库 IO + 一个写事务；而且它与 §5.3 的 `owner.sqlite` 是同一个东西——**`owner.sqlite` 本身就是分片的单点依赖**，把发号也压上去会让"单点"从"影响写路由"扩大到"影响一切新建" | ⚠ 备选（只在"区间不够用"时才考虑，而区间**永远够用**，见下） |
| **(C) 其他全局唯一 id 生成法（UUID / ULID / Snowflake / 哈希）** | — | — | ❌ **在本项目里不可行，而且有一个"静默毁数据"的具体机制** | ❌ **明确否决**，理由见下 |

**为什么 (C) 不是"更好"，而是不可行**（两条都是本次实测的硬约束）：

1. **R*Tree 的 id 必须是整数，而且非整数会被静默吞掉。** 实测：`CREATE VIRTUAL TABLE r USING
   rtree(id, …)` 之后插入字符串 id `'uuid-abc'`，SQLite **不报错**，而是把它存成了
   **`id = 0`（integer）**，再用 `'uuid-abc'` 去查返回 **0 行**。
   三个空间索引的声明就是 `USING rtree(id, min_lon, max_lon, min_lat, max_lat)`
   （实测 `sqlite_master` 原文）⇒ **换成 UUID/字符串 id，等于把整张空间索引写成垃圾，
   而且不报错。** 这不是"要改很多代码"，这是"数据会被静默毁掉"。
2. **id 必须留在 `Number.MAX_SAFE_INTEGER` 以内。** 实测：往 `node:sqlite` 里写
   `9,007,199,254,740,993`（= `MAX_SAFE_INTEGER + 2`）能写进去，但**读回来时直接抛
   `RangeError: Value is too large to be represented as a JavaScript number`**
   （除非用 `new DatabaseSync(path, { readBigInts: true })`，实测该选项**能**精确读出）。
   全项目的 id / 引用列都是 `INTEGER`（实测：`nodes.id` / `ways.id` / `relations.id` /
   `way_nodes.way_node_id,node_id` / `relation_members.member_ref` / `changes.elem_id` /
   `stations.node_id,way_id`），而且 `IdAllocator` 全程用 JS `Number` 运算
   ⇒ **id 区间必须整体压在 ~9.0×10¹⁵ 以下**。

**Snowflake 这类"时间戳+机器号"方案为什么也没意义**：它解决的问题是"多写入者 + 时钟"，
而我们这里**每片只有一个写入者（一个进程、一把 SQLite 写锁）**，
要的只是"分片之间不重叠"。Snowflake 会把 id 撑到 19 位（逼近上面那条 9×10¹⁵ 的线），
换来的能力（按时间有序、去中心化）这里一个都用不上。**(A) 是同一件事的极简形式。**

#### 5.9.3 (A) 的具体区间方案（可直接实现 + 可断言）

```js
// 常量（写进 config.json 或代码常量；一旦上线不得更改）
const ID_PLAN = {
  node:     { base: 10_000_000_000_000,  band: 10_000_000_000 },  // 1e13, 每片 1e10 个号
  way:      { base: 100_000_000_000_000, band: 10_000_000_000 },  // 1e14
  relation: { base: 1_000_000_000_000_000, band: 10_000_000_000 } // 1e15
};
const MAX_SHARD_INDEX = 262_143;   // 2^18 - 1，与 band 一起保证上限不越界（见下）

// 某片的区间
idRange(type, shardIndex) = [ base[type] + shardIndex*band, base[type] + (shardIndex+1)*band )
```

**为什么是这几个数（三条都验算过）**：

| 约束 | 验算 |
| --- | --- |
| **必须高于全世界已有的所有 id**（这样"新号 vs 存量"永不相撞，**不需要枚举任何存量**） | 实测三个库的最大 id：node **14,201,758,760**、way **1,560,854,633**、relation **21,408,527**。`node.base = 1e13` 比最大 node id 高 **约 700 倍**；真实 OSM node id 按每年约 5×10⁸ 增长，要 5000 年以上才够到 1e13 |
| **必须低于 `Number.MAX_SAFE_INTEGER`** | 最大可能是 relation：`1e15 + 262144×1e10 = 1e15 + 2.62144e15 = 3.62e15` < **9.007e15** ✓（余量 2.5 倍） |
| **三类之间也要互不重叠**（防御"跨类型写错"） | node 上界 `1e13 + 2.62e15`… ⚠ **不成立**——见下方修正 |

> ⚠ **上面第三条我要修正自己**：`band = 1e10 × 262,144 片 = 2.62e15`，这比 `way.base = 1e14` 大得多，
> 所以**node 的区间会盖住 way 的区间**。真实项目不可能有 26 万个分片（试点 8 片），
> 但"以后会不会有"这种话不该写进设计。**改成让 band 随类型收紧 + 把分片数上限写死**：

```js
// 修正版：band 取"每片一辈子都发不完"的最小值，并显式限死分片数
const ID_PLAN = {
  node:     { base: 10_000_000_000_000,     band: 100_000_000 },  // 1e13, 每片 1e8 个号
  way:      { base: 100_000_000_000_000,    band: 100_000_000 },  // 1e14
  relation: { base: 1_000_000_000_000_000,  band: 100_000_000 }   // 1e15
};
const MAX_SHARD_INDEX = 8_191;   // 2^13-1，够 8192 片
```

**修正后的验算**：

| 约束 | 结果 |
| --- | --- |
| node 区间上界 | `1e13 + 8192×1e8 = 1e13 + 8.192e11 = 1.0819e13` **< way.base 1e14** ✓（类型间不重叠） |
| way 区间上界 | `1e14 + 8.192e11 = 1.00819e14` **< relation.base 1e15** ✓ |
| relation 区间上界 | `1e15 + 8.192e11 = 1.00082e15` **< 9.007e15** ✓（余量 9 倍） |
| 每片能新发多少号 | **1 亿**个。实测今天全库一共 14.8 万次 change（`osm.sqlite` 14,793 / 731 changeset）⇒ 1 亿是**三个数量级的余量** |
| 分片数上限 | **8,192**（远超试点的 8 片，也远超 §5.8.4 裁片后的两位数） |
| **新 id vs 存量 id** | 所有新 id ≥ `1e13` > 全库最大 id `1.42e10` ✓ **全局、永久、无需枚举** |

**实现改动面（很小，且不外溢）**：

| 改动 | 文件 | 说明 |
| --- | --- | --- |
| `IdAllocator` 支持 `base` + 上界断言 | `server/dbschema.js`（≈547~568 行） | 构造函数多一个 `{ base, limit }`；`alloc()` 在 `id >= limit` 时**抛错**（不是回绕、不是静默继续）。**默认不传 = 今天的行为逐字节不变** |
| `OsmDB` 把片的区间传下去 | `server/osmdb.js`（≈1686 行） | `new IdAllocator(this.db, this._idRange)`；区间从 shard 的 `meta.id_base_*` 读，或由 `regiondb` 注入 |
| 分片打开时校验区间 | `server/regiondb.js`（新） | 读 `meta.id_base_node/way/relation`、`meta.id_band`、`meta.shard_index`；缺任何一个 ⇒ **只读降级 + ERROR**（不许在"没有区间"的片上开写） |

#### 5.9.4 导入器怎么配合（你的第 2 点）

**谁决定 `id_base`：注册表决定 `shardIndex`，导入器只负责把它翻译成区间写进库里。**

- **注册表**（§2.2）里每片加两个字段（这是**唯一出处**，也是你可断言的依据）：
  ```jsonc
  "bj-1": { ..., "shardIndex": 0 },
  "lf-1": { ..., "shardIndex": 1 },
  "tj-1": { ..., "shardIndex": 2 }
  ```
- **导入器**：`tools/import-osm.js` 现在写 `next_*_id = 源文件最大 id + 余量`
  （第 **515 / 597 / 752~754** 行）。分片模式下改为：

```
新增 CLI：--shard-index N   （或 --city/--region <id> + --registry data/regions/registry.json）
行为差异（只在给了 --shard-index 时生效）：
  ① meta.next_node_id     = ID_PLAN.node.base     + N*band
     meta.next_way_id     = ID_PLAN.way.base      + N*band
     meta.next_relation_id= ID_PLAN.relation.base + N*band
     （**不再写 max(id)+余量** —— 那正是问题 B 的来源）
  ② 额外写：meta.id_base_node / id_base_way / id_base_relation / id_band / shard_index
  ③ 导入结束后自检（失败就 exit != 0，不留一个"看起来能用"的片）：
       MAX(nodes.id)     < ID_PLAN.node.base      // 源文件里的 id 必须都在区间之下
       MAX(ways.id)      < ID_PLAN.way.base
       MAX(relations.id) < ID_PLAN.relation.base
       next_node_id === ID_PLAN.node.base + N*band   // 三个都逐位核对
```

- **`tools/merge-osm.js` 也要跟着改**：它现在的口径是"`next_*_id` 必须取大"
  （第 **248** 行附近），分片模式下应当**保留目标的区间**而不是取两边的 max。
  （这条也是 §11.2 里已列的坑之一，现在有了明确的动作。）
- **不加 `--shard-index` 时，导入器行为逐字节不变** ⇒ `import-test`(82) / `pbf-import-test`(149)
  不受影响（它们不传这个参数）。

#### 5.9.5 已有数据的迁移（你的第 3 点）：**绝不重编号**

现状实测：`data/osm/osm.sqlite` 里**已经存在**老分配器发出的玩家元素
（`next_node_id = 14,172,804,683`，`MAX(nodes.id) = 14,172,804,682`；
`changes` 里 635 条 node `create` / 184 条 way `create`，`changesets` 731 个）。

**为什么绝不重编号**（三条都是硬的）：

1. **`changes` / `changesets` 会全部指向错误的元素**（实测 14,793 条 change / 731 个 changeset，
   其中 43 个 changeset 被回滚过）。重编号 = 撤销与变更集回滚**静默失效**（指向别的元素），
   这比"重编号失败"更糟，因为它不报错。
2. **`stations.node_id` / `stations.way_id` 会断**（实测 67 个车站，`node_id` 全部可解析）。
   站点吸附关系是玩家资产的**语义核心**（§6 全篇建立在这上面）。
3. **`relation_members` / `way_nodes` 是 id 引用**（实测 325,804 / 2,677,174 行），
   重编号要同时改 5 张表 + 3 个 R*Tree + 8 个玩法表的引用列——**一个事务里做不完，
   中途失败就是一个"半重编号"的库**，而这种状态没有工具能修。

**所以迁移规则是**：

```
① 老库（osm.sqlite）里的存量 id 一律【保持不动】。
② 该片（bj-1）的区间指向 shardIndex=0 —— 它的 base（1e13…）本来就【高于所有存量 id】
   （实测存量最大 1.42e10 < 1e13，差 700 倍）⇒ 不需要为存量"腾地方"，
    也不需要知道存量都有哪些 id。这是 (A) 方案最省事的地方。
③ 游标重置：把该片的 meta.next_*_id 从"老游标"（14,172,804,683 / …）
   改成"区间起点"（1e13 / 1e14 / 1e15）。这是一个【单向、幂等】的显式迁移步骤，
   必须在 P2 上线写入路由【之前】做完，并用下面 5.9.6 的断言核对。
④ 老游标不能丢：迁移时把它记进 meta.id_cursor_legacy_*（只作考古用，不参与分配）。
```

**为什么 ② 能成立、而且这么好**：因为 `base > 一切存量 id` 是**一个不变量**，
  而不是"一份需要维护的清单"。老库有多少玩家元素、都在什么 id 上，**完全不用管**。

**⚠ 一个必须一起改的地方**：`IdAllocator` 的构造函数有回退逻辑
`Number(getMeta(db,'next_node_id',0)) || (SELECT MAX(id)+1 FROM nodes)`
（`dbschema.js:551~553`）。如果某片的 `next_node_id` 是空/0，它会回退到 `MAX(id)+1`
——**那就会绕过区间，重新掉进问题 B**。所以分片模式必须：
**`meta.next_*_id` 缺失或为 0 时直接抛错，禁止回退**（回退只在"非分片模式"下保留）。

#### 5.9.6 你可断言的验收条件（你的第 4 点，写成可执行的形式）

```
断言 1【分片之间 id 区间不相交】
  for each shard s in registry:
      read meta.id_base_node/way/relation, meta.id_band, meta.shard_index from s
      assert meta.shard_index === registry[s].shardIndex
      assert meta.id_base_node     === ID_PLAN.node.base     + shardIndex*band
      assert meta.id_base_way      === ID_PLAN.way.base      + shardIndex*band
      assert meta.id_base_relation === ID_PLAN.relation.base + shardIndex*band
  for each pair (s, t), s ≠ t:
      assert 区间(s, type) ∩ 区间(t, type) === ∅            // 由 shardIndex 互异 + band 固定直接推出
  更省事的等价断言（只比两端，不需要两两比较）：
      assert max(shardIndex) < MAX_SHARD_INDEX
      assert 所有 id_base_* 两两不同  ⇒ 区间两两不相交

断言 2【新元素的 id 落在本片区间内】
  对每片 s、每个 type：
      assert 本片所有元素 id < id_base + band          // 新发的号不会越界
      assert meta.next_*_id ∈ [id_base, id_base + band) // 游标在区间内
  运行期（最直接的一条，可以做成 --regions-audit 的一项）：
      新建一个元素 → assert id_base ≤ 新 id < id_base + band
      且 assert 新 id 在【其它片】里查不到

断言 3【新 id 不撞存量】（这一条让"新 id vs 老数据"永远安全）
      assert MIN(ID_PLAN.node.base)     > 所有分片的 MAX(nodes.id)
      assert MIN(ID_PLAN.way.base)      > 所有分片的 MAX(ways.id)
      assert MIN(ID_PLAN.relation.base) > 所有分片的 MAX(relations.id)
      // 实测今天：1e13 > 1.42e10 ✓ ；1e14 > 1.56e9 ✓ ；1e15 > 2.14e7 ✓

断言 4【上线前的一次性核对】（迁移 ③ 做完之后跑一次就够）
      真正新建一条 relation/node/way，断言 id === id_base（第一发必须是区间起点）
```

**这四条断言里，断言 1 与 3 是纯静态的**（只读 `meta`，不依赖任何运行状态），
**所以可以放进注册表自检，在"打开分片"这一步就跑**——这正是 §2.3 那 5 项自检的位置。

### 6.1 现状（核实过的事实）

### 6.2 方案 (a)：交通数据独立成一个库（**推荐**）

```
data/transit/transit.sqlite      ← companies / stations / lines / vehicles /
                                   line_daily_stats / sim_state /
                                   population_cells / population_sources
data/regions/*.sqlite            ← 只剩 OSM 表（nodes/ways/relations/way_nodes/
                                   relation_members/三个 R*Tree/changes/changesets/meta）
```

**为什么推荐**：

1. **分片变成"干净的 OSM 提取包"**。这带来一串连锁好处：分片可以用现成的导入器重新生成、
   可以整片替换、可以拿去和 Geofabrik 的包逐要素比对、可以 `VACUUM INTO` 后单独归档。
   如果玩法表混在里面，**每个分片都是一个不同的 schema 变体**，第 11 节的迁移与回滚会立刻变复杂。
2. **玩法数据今天只有几十 KB 级别**（67 车站 + 4 线路 + 35 车辆 + 2 公司 + 731 changeset + 14,793 change +
   19,520 人口格），独立成库的**代价极小**。
3. **符合"玩家存档跟人走"的产品语义**：玩家换区域/换城市，公司还是他自己的（`companies.owner`
   是玩家 id，`data/users.json` 全局一份，见 `deploy/CITIES.md` 第 84 行）。
4. **`refs` / `owner` / `idband` 已经是一个独立小库**（5.3），交通库与它是同一个模式，
   运维心智一致。

**改动面（逐个文件）**：

| 文件 | 改动 | 风险 |
| --- | --- | --- |
| `server/index.js`（装配，第 262 / 276 / 288~318 行） | **多建一个 `DatabaseSync(config.transitDb)`**，用 `openDatabase()` 保证 schema；`OsmOps` 仍拿 `db`（OSM）；`Transit` 拿 `transitDb`；`Population` 拿**两个**（读 OSM、写 transit） | 中。这是唯一必须改的装配点，也是唯一会出现"两个句柄"的地方 |
| `server/transit.js` | **一行不改**（它只用构造时传入的 `db`） | 低。⚠ 前提是 `Transit` 里没有跨表 JOIN OSM 的 SQL —— **本次未逐条核对 9,007 行的所有 SQL**，P3 开工前必须 `grep` 一遍 `FROM nodes|ways|relations`。**未验证** |
| `server/population.js` | 构造改成 `new Population(osmDb, { store })` 之类的双句柄；`_st` 里的 `taggedWays/wayNodes/nodeById` 走 OSM，`population_*` 走 store | 中。`Population` 内部有跨表逻辑（`buildAll` 第 864 行、`cellsInBbox` 第 1022 行） |
| `server/dbschema.js` | 把玩法表的 DDL 拆成 `TRANSIT_SCHEMA_SQL`，`SCHEMA_SQL` 保留 OSM 部分；两个库都建各自的表 | 中。`migrate()` / `migrateCompanies()`（第 241 / 301 行）要跟着拆 |
| `server/osmops.js` | 一行不改 | 低 |
| `tests/**` | **多套**（见第 9 节） | 高。`tests/transit-e2e.js:110` 直接 `require('../server/osmdb')`，`transit-e2e.js:151` 直接开 `node:sqlite` 查库断言；拆库后它们查的是"OSM 库"，如果断言里读了 `stations` 就会失败 |

**迁移代价**：把 9 张表从 `osm.sqlite` **复制**到 `transit.sqlite`（`ATTACH` + `INSERT INTO … SELECT`，
实测 ATTACH 可用）。**不删原表**（第 11 节回滚靠它）。

**取舍（代价）**：

- **失去原子性**：今天"编辑一个 way → 更新人口网格 → 更新线路路径"在同一个 sqlite 连接上；
  拆库后跨两个连接，`BEGIN` 不覆盖对方。
  **缓解**：这些都是**派生数据**（人口网格可从 OSM 重算，线路路径可从图重算），
  失败可重算 ⇒ 接受最终一致。但**必须**保证顺序与重试：先写真相（OSM），再写派生（人口/路径），
  派生失败入重试队列。现有的 `onOsmWaysChanged`（`server/index.js` 第 591~632 行）
  已经是"收集 dirty → 600 ms 后 flush → 逐条 try/catch"的结构，**正好容纳重试**。
- **更多连接**：每个分片一个连接 + owner + transit。SQLite 连接不是稀缺资源（今天的瓶颈是
  `node:sqlite` 是同步 API、单线程），但要设上限。

### 6.3 方案 (b)：交通数据留在"主片"

```
data/regions/bj-1.sqlite   ← OSM 表 + companies/stations/lines/vehicles/sim_state/…
data/regions/tj-1.sqlite   ← 只有 OSM 表
```

**改动面**：几乎为零。`server/index.js` 第 262 行的 `db` 就是主片的 `OsmDB`；
`Transit(db)` / `Population(db)` / `RailGraph(db)` 全部照旧拿到同一个主片句柄。

**代价**：

1. **主片不再是纯 OSM 提取包** ⇒ 第 11 节的"整片替换 / 重新派生"不再可行。
2. `stations.node_id` / `way_id` 指向的 OSM 元素**可能属于别的片**（玩家在北京修到廊坊的线，
   廊坊侧的节点在 `lf-1`）。今天 `_wayOfNode`（`transit.js` 第 3472 行附近）在内存图里查，
   而内存图是**按片**建的 ⇒ 跨片就查不到。
3. 主片的 schema 与其它片不同 ⇒ 所有"遍历分片"的运维脚本都要特判。

**结论**：(b) 唯一的优势是"零改动"，但它把复杂度推给了后面每一步。

### 6.4 推荐：(a)，并且**分两小步落地**

- **P3a**（低风险）：把 **`population_cells` / `population_sources`** 先搬出去（它们是纯派生、
  键是绝对坐标、和玩法无关），同时把玩法表**原地保留**在主片。
  → 此时分片已经是"OSM + 少量派生表"，先验证"跨库写非原子"能不能被 `onOsmWaysChanged` 兜住。
- **P3b**：搬 `companies / stations / lines / vehicles / line_daily_stats / sim_state`。
  → 分片彻底变干净。

**`changes` / `changesets`（编辑历史 / 回滚）放哪** —— 这是 (a)/(b) 之外**必须单独决定**的一项：

| 选项 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 跟交通库放一起（"玩法库"） | 回滚与撤销的时间线统一；`changes` 会引用元素 id，和玩家资产同源 | `changes` 会**线性增长**（实测已 14,793 行 / 731 changeset），和交通库混在一起后无法单独清理 | ⚠ 可接受 |
| **放 owner 库**（推荐） | owner 库本来就是"元素 → 位置"的权威索引，`changes` 也是"元素的历史"，语义同族；写入路径都在一次 `BEGIN IMMEDIATE` 里；分片保持纯净 | owner 库会变大 | ✅ **推荐** |
| 每个分片各存自己的 `changes` | 与元素同片、天然一致 | **撤销/回滚跨片时要查多个库**；`/api/history` 要做 N 路合并；实验证明最痛 | ❌ |

**实测支持推荐**：`changesets` 731 行、`changes` 14,793 行、43 个 changeset 被回滚过、
12,059 条 change 已被 undone —— 历史数据量很小，集中在一处毫无压力。
而且 `/api/history`（`server/index.js` ≈第 1737 行）今天就已经在做"全库最近 N 条"，
集中存放让它**不用改**。

### 6.5 跨片吸附与跨片寻路（核心难点）

**问题**：一条从北京修到廊坊的线，铁路网在片 A、片 B 各有一部分，路径怎么算？

#### 6.5.1 先解决"节点 id 会不会撞"

- **基础图节点（OSM node id）不会撞**：id 是全局的。**实测证据**：`hebei-only.sqlite` 与
  `osm.sqlite` 共有的 110,766 个 node id **逐字相同**、坐标一致。
- **虚拟路口 id 会撞**：`VIRTUAL_NODE_ID = -1`（`railgraph.js:81`），
  虚拟 id = `-1 - _vnodeSeq++`（第 405 行）⇒ **每个 `RailGraph` 实例都从 −1 开始编号**。
  两个实例合并，第一片有 500 个虚拟路口（−1…−500），第二片也有 500 个（−1…−500）⇒ **全撞**。
- **平面投影基准不同**：`_planar`（第 438 行）把 `_kx` 定在**第一条路段**的纬度上，
  `_reindexSegments`（第 501 行）又用 `refLat` 重设。两个实例的投影不同 ⇒
  `JUNCTION_SNAP_M = 1.5 m`（第 87 行）的"交点吸附"在两片之间**不可比**。

> **结论：绝对不能把两个 `RailGraph` 实例"拼"起来用。** 这不是"可能有问题"，是必然出错。
> 这条是本设计里最硬的"不要做什么"。

#### 6.5.2 三种方案

| 方案 | 做法 | 正确性 | 成本 | 结论 |
| --- | --- | --- | --- | --- |
| **(A) 拼图** | 两个 `RailGraph` 实例共享 `nodes` Map | ❌ 虚拟 id 与投影都撞 | — | ❌ 禁止 |
| **(B) 分段最短路拼接** | 在每片图上各跑 `shortestPath`，在共用节点处接起来 | ⚠ **不保证最优**（跨片换乘点选错会绕路），但**只要两个站之间有至少一个共用节点就一定能通** | 低（复用现有 `shortestPath`） | ⚠ 备选 |
| **(C) 按需拼接建图（推荐）** | 对"这条线路覆盖的走廊 bbox"**临时拼出一份 OSM 视图**，在它上面**新建一个** `RailGraph`，跑完整的 `routeThrough` | ✅ 与单片完全同源、同语义 | 建图成本 ∝ 走廊大小（远小于全库）；可缓存 | ✅ **推荐** |

**(C) 的具体做法**：

```
走廊 bbox = 线路所有站点的 bbox，每边外扩 pad（建议 = 相邻两站最大间距 × 1.5，
            且不小于 5 km —— 保证"绕行"的替代路径也在框内）
   ↓
对每个相交分片，查两件事（只读）：
  ① ways: WHERE deleted=0 AND tags LIKE '%railway%' AND <bbox 相交>
  ② 这些 way 的 way_nodes → 节点 id 集合
  ③ 节点 id 按 owner.sqlite 分组 → 向各自属主片按 id 批量取 nodes
     （跨片取节点用 5.4 的副本也行，但走廊可能超出预先复制的边界 ⇒ 直接按 id 取更稳）
   ↓
在内存里合成一个临时 OSM 视图（不落盘），RailGraph 从这个视图建图
   ↓
transit.routeThrough(stopNodeIds) 照旧 → path / path_len / path_error
```

**这样做的三个好处**：

1. **不需要改 `RailGraph` 一行**：它已经支持"从 db 取数"，只要给它一个**同样的语句接口**
   （`_st.railWays.all()` / `wayNodes.all()` / `nodeById.get()` / `wayById.get()`，
   `railgraph.js` 第 248~253 行）。临时视图实现这四个方法即可。
   ⚠ **但注意**：`server/index.js` 的切片建图 `buildGraphSliced`（第 355 行）还额外要求
   `_st.railWays` 有 `.iterate()`（第 361 行会检查）；临时视图要么也提供 `iterate()`，
   要么走廊建图走一次性 `build()`（走廊不大，同步建图可接受，但**会阻塞事件循环** ——
   必须用现有的切片路径，否则违反"不锁事件循环"的既有承诺）。
2. **正确性由构造保证**：完整的走廊数据 → 一张完整的图 → 与单片行为逐字节相同。
3. **它本身就是目标**：这正是用户要的"按区域惰性构建"——**只为玩家真正要用的那块建图**，
   而不是为整个数据集建图。

**代价与风险**：

- **走廊 bbox 内的数据量决定建图时间**。北京→廊坊的走廊约 60×40 km。**未实测**：
  走廊建图耗时可参照"铁路网全库 0.8 s / 91,873 条道路 10.1 s"（`server/index.js` 第 323~325 行注释）
  按 way 条数比例外推，**但这是估算，必须实测**。
- **缓存与失效**：走廊图按 `(bbox 量化到 0.05°, 片集合)` 做 key 缓存，TTL + LRU（建议 TTL 5 分钟、
  上限 4 张）。**失效信号**：现有的 `rail.updateWay(id)` / `transit.onRailChanged(ids)`
  （`server/index.js` 第 605 / 619 行）会告诉我们是哪条 way 动了 → 命中走廊就直接作废。
- **公交（bus）模式更贵**：道路网是 91,873 条 way / 107 万段（`:323` 注释），走廊建一张路网
  可能几秒级。**缓解**：公交的吸附默认**不限距离**（`busSnapMeters: 0`），
  意味着它比铁路更容易需要"跨到很远"——这会让走廊变得很大。**建议在试点期把
  `config.transit.busSnapMeters` 显式设一个上限（如 2000 m）**，并在城区内保持走廊小。
  ⚠ 这会改变游戏行为（今天的默认是"多远都吸"），**属于 H1 的边界，需要用户确认**。
- **站点吸附（跨片）**：吸附目标是内存图。若站点吸附由走廊图完成，站点的 `node_id` 可能属于
  另一片 ⇒ 再次触发 5.4 的副本与 5.5 的 id 问题。
  **推荐**：**站点吸附只允许用"站点所在片"的图**（`homeOf('node', station.lat/lon)`），
  跨片吸附（"北京站点吸到廊坊的轨道上"）**直接报错并说明原因**——这与今天
  "120 m 以内没有轨道就报错"的语义一致（`transit.js` 第 3466 行附近），
  只是把"距离不够"换成"不在同一分区"。**取舍**：这会让"边境车站"变难建；
  但反过来，"跨片吸附"会产生一个 `node_id` 属于别片的车站，后续每次编辑都要跨库校验，
  复杂度不值得。**建议在注册表里允许片之间定义 `snapNeighbors`（默认全部相邻）**，
  需要时放开。

### 6.7 分片库里"自带一整套交通玩法表"怎么处理（**你指出的问题 ①，我的推荐 + 改动面**）

**先把实测摆清楚**（见事实 7）：`tools/import-osm.js` 走的是 `server/dbschema.js` 的**全套 `SCHEMA_SQL`**，
所以每个分片库都会长出一整套交通表。而且**"留空不用"是不稳定的**：
`beijing` 分片在被人起过一次服务之后，`population_cells` 已经是 **24,650 行**、
`population_sources` **133,920 行**（`server/index.js` ≈第 549~559 行"空就 `buildAll()`"那段填的）；
`hebei` 分片没被起过服务，所以还是 0 行。

#### 6.7.1 三个方案的逐一评估（含改动面）

| 方案 | 做法 | 改动面 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| **① 只当几何用，交通表留空/不用** | 什么都不改，文档里写"分片里的交通表不要用" | **零代码改动** | ⚠ **不稳定**：实测会被 `buildAll()` 自动填（24,650 + 133,920 行）；且"谁会误用"没有任何技术栅栏——`new Transit(shardDb)` 一行就能接上去 | ❌ 不作为最终方案，只作为 P0/P1 的**过渡** |

```

  · 分片用【只读连接】打开（readOnly: true），并在 OsmDB 加一个 readOnly 选项，

    （注：这三段本来就有 try/catch 兜底 —— osmdb.js ≈第 1749 行的注释明说

P2/P3（与写入路由一起做）：
  · ② 给 dbschema 加 schema 模式，新导入的分片【从建库那一刻就不含交通表】。
  · ③ 交通表迁到 data/transit/transit.sqlite（§6.2 方案 a），把 beijing 分片里
    那 15.8 万行 population_* 直接丢弃并重算（它是纯派生数据）。

P4：
  · 分片彻底变成"纯 OSM 提取包"，与 §11.1 "分片 = 可整片替换的 OSM 提取包" 的目标态一致。
```

**为什么推荐"只读 + 不接线"作为 P0/P1 的过渡，而不是先做 ②**：

- ② 要动 `server/dbschema.js`，而它是**所有测试套件的地基**（`import-test` 82 项、`pbf-import-test` 149 项
  都在断言 schema 与导入结果）。P0/P1 的目标是"最小可验证切片、一行回滚"，
  把这个风险提前进来不划算。
- "只读 + 不接线"是**零 schema 改动 + 强栅栏**：分片根本不被任何玩法组件持有，
  所以"误写"在 P0/P1 是**结构上不可能**，而不是"文档里说了别写"。
- 而且它**顺带解决了一个必须解决的问题**：现在有人对 `beijing` 分片起过服务，
  说明"分片可能被当成一个普通数据集启动"——**用只读打开会立刻暴露这件事**
  （`OsmDB` 的自愈/回填会失败并打 WARN），比等着它悄悄被填满好。

**③ 的一个额外好处（值得单独说）**：把 `population_*` 移出分片之后，
**分片之间的 `population_cells` 就可以按 `(cell_x, cell_y)` 主键直接相加**——
实测 `population_cells` 的主键就是 `(cell_x, cell_y)`、而 `cellOf` 用的是**绝对经纬度**
（`server/population.js` ≈第 168 行的 `CELL_M = 250` 与第 569~577 行的 `cellOf`/`cellCenter`），
所以它天然是"全局 250 m 网格"，跨片求和没有冲突（除了重叠区会被重复计数——那正是
§5.8 让镜像片退出的另一个理由）。

## 7. 惰性建图 / 启动

### 7.1 "激活区域"的定义

```
active(shard) :=
    shard ∈ viewportShards(任一在线玩家上报的视口)        ← 实时
  ∪ shard ∈ assetShards(stations/lines/vehicles 所在片)   ← 常驻
  ∪ shard ∈ config.regions.alwaysActive                   ← 运维强制
```

**视口信号已经有了，不需要新协议**：`transit.setPlayerView(userId, view)` 由 WebSocket 消息驱动
（`server/index.js` 第 894~903 行一带：`view.radiusM` 上限 `LIMITS.transitViewRadiusM = 12000`）。
**这就是"玩家看得到哪一块"的现成信号**，直接拿来当激活输入。

**取舍**：

| 激活策略 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **视口驱动**（推荐） | 零新协议；天然"用哪建哪" | 玩家快速平移时会反复激活/卸载 | ✅ 配冷却（见 7.2） |
| 有资产就激活 | 模拟不会因为卸载而断 | 资产分布可能很广 | ✅ **叠加**上去（`assetShards` 常驻） |
| 显式开关（config 列白名单） | 运维可控、可预热 | 需要人维护 | ✅ **叠加**（`alwaysActive`） |
| 玩家登录即全建 | 无卡顿 | 等于没做惰性 | ❌ |

### 7.2 图的生命周期与释放

```
状态机：  absent → building → ready → idle → unloading → absent
                                    ▲                    │
                                    └── 玩家回来（重建） ──┘
```

- `building`：走**现有的切片路径** `buildGraphSliced(graph, {estimateMs, onProgress})`
  （`server/index.js` 第 355 行）——**必须**，否则 10 s 的同步建图会锁住事件循环，
  违反第 325~327 行注释里明确承诺的"端口开着也要能响应"。
- `ready → idle`：最后一名玩家离开该片视口（或不再有资产引用）后 `regions.graphIdleMs`（建议 10 min）。
- `idle → unloading`：`graph.nodes.clear(); graph.wayInfo.clear(); graph.wayNodes.clear();
  graph._segGrid = null; …`（与 `railgraph.js` 第 320~330 行 `build()` 开头的清理同一套），
  然后置引用为 `null` 交给 GC。**先打一行日志写明"卸载了什么、多少内存、下次重建预计多久"**。
- **永不卸载**：`assetShards` 里的片（有车站/线路/车辆）。理由见 R28——否则一次 tick
  要等 10 s 重建。
- **重建惩罚的缓解**：**先预热再卸载**不现实（内存只增不减）；实际做法是
  **在玩家视口切换到新片时立刻开建，并让 `/api/ready` 之外再加一个
  `regions` 子状态**（见 7.3），前端暂时不动（客户端不改）。

### 7.3 对现有启动流程的影响

现状（`server/index.js`，快照 `7355F6E8D3E2`）：

```
boot()  ≈第 2186 行
  ├─ httpServer.listen(...)                    ≈第 2190 行   ← 端口先开
  └─ runInit()  ≈第 2170 行（不 await）
       └─ initTransitWorld()  第 523 行
            ├─ setInitStage('rail')       → buildGraphSliced(rail)        第 527 行
            ├─ setInitStage('road')       → buildGraphSliced(road)（惰性判据 needsBusGraph，≈第 2130 行）
            ├─ setInitStage('population') → 首次 buildAll()（分钟级同步循环！）
            └─ setInitStage('paths')      → transit.onRailChanged()（同步）
       └─ finishInit()  ≈第 2148 行 → initState.done = true → /api/* 放行
INIT_STAGES = [rail 5, road 84, population 6, paths 5]   （第 2021 行，权重合计 100）
```

**改造方案（保持 `/api/ready` 的形状不变）**：

1. `INIT_STAGES` 的 `road` 权重 84 是**为全库路网定的**。改成按激活区域建之后，
   启动阶段只建 `alwaysActive` + `assetShards`（实测：**当前唯一的资产片就是主片**，
   67 个车站全在 lat 39.896~39.943 / lon 116.185~116.430），所以启动时间会**直接下降**。
2. **新增一个 `regions` 阶段**（排在 `paths` 之后），负责"非启动片的按需建图"。
   关键设计：**它不进 `initState.done` 的判据**——`ready=true` 仍然只表示"可以接请求"，
   与今天语义一致；区域建图的进度只作为 `progress.regions` 的**附加字段**回显
   （用 `initPayload()` 的既有结构，≈第 2048 行）。
   **理由**：如果让 `ready` 等所有区域建完，就等于把惰性建图变回全量建图（违反设计目标）。
3. `finishInit()`（≈第 2148 行）里的 `transit.onRailChanged()` 是**全量重建线路路径**
   （第 568 行附近注释"不是增量"）。分片后它必须**逐区域**跑，并且只对"路径真的踩到
   那个片"的线路跑。现有的增量入口 `transit.onRailChanged(ids)`（`transit.js` 第 8563 行）
   已经支持按 way id 过滤，直接复用。
4. **人口网格是最大的不确定性**：`population.buildAll()` 是"一次性整段同步循环，
   从外面没有分批入口"（`server/index.js` 第 553~557 行注释），**分钟级**。
   分片后它天然变成"逐区域 buildAll"，**每个区域的循环更短**，但**仍会各自阻塞事件循环**。
   缓解：按 `graphSliceMs` 的思路给 `population.js` 加分批入口（**要改 `population.js`**），
   或者在**服务启动后的空闲窗口**里逐区域跑。⚠ **这是 P4 里最大的未知数，未实测。**

## 8. 性能预期与验证方法

### 8.1 为什么**可能**更好，以及为什么**可能更差**（如实）

**可能更好的只有这四条**：

1. **启动时间**：铁路网 + 道路网 + 人口网格今天都是**全库**的（`railgraph.js:249` 的
   `WHERE tags LIKE '%highway%'` 一次扫全库；`population.js:590` 同）。分区后只为激活区域建。
   今天实测的路网规模：91,873 条道路 / 107 万段 / 87 万节点 / 10~18 s
   （`server/index.js` 第 323~325 行注释 + 第 542 行日志格式）。
2. **常驻内存**：稳态 RSS 0.55~0.85 GB（`deploy/DEPLOY.md:25`）。只为激活区域持有图 ⇒ 下降。
3. **不让新城市拖慢老城市**：这是 H2 的真正含义。加天津/保定之后，单库方案的这三项会**线性变差**，
   分区方案把它们挡住。
4. **单片直通时的"白送"收益**：命中单片时，查询在小库上跑**同一段代码**。
   索引里的无关行更少（比如 `idx_ways_lod_zoom` 在 z10 是 26,921 行），
   页面缓存压力更小。

**明确不会更好的（本次实测推翻了设计直觉，见事实 2）**：

- z10~z15 的 POI 扫描（走 `idx_nodes_poi_low`，**全库只有 2,416 行**，实测 z10 7.3 ms）；
- z13~z16 的 way 扫描（R*Tree 驱动，实测 z13 780 ms 对应 126,743 行**全在视口内**）；
- 任何在 z ≥ 13 的视口查询。**行都在视口里，分片切不掉。**

**可能更差的（H2 的真实威胁）**：

- **低缩放扇出**：z ≤ 12 的视口跨度 2.115°(z10) / 1.057°(z11) / 0.529°(z12)，会覆盖多片；
  扇出 N 次查询 + 合并 = 同样的候选行 + N 份固定开销 ⇒ **净更慢**。
- **折线合并预算 N 倍**：`COALESCE_DEFAULTS.budget` 每片独立（4.3），多片时 `displayLines`
  总量可能上涨 ⇒ payload 变大。
- **`limit` 打满更频繁**：多片各自返回完整结果，合并后更可能超过 `viewportLimit` ⇒
  `truncated=true` ⇒ 客户端拆更多块 ⇒ **更多请求**（这是最隐蔽的变差方式：单次请求没变慢，
  但请求数上升）。

**对策（已在前面各节定死）**：`fanoutMax=2`、`fallbackBelowZoom=11`、`mergedBytesLimit=4 MB`、
多片时 `budget/N` 摊薄、`truncation.complete` 用 `AND`。

## 11. 数据迁移与回滚

### 11.1 最重要的原则：**不要迁移，要派生**

现有 `data/osm/osm.sqlite`（555,581,440 B，含 731 个 changeset / 14,793 条 change /
67 车站 / 4 线路 / 35 车辆 / 2 公司 / 19,520 人口格）是**玩家的存档**。
"把库切开"这个动作本身有太多能出错的地方（几何重算、物化列重填、索引重建、
id 分配器、软删除的 deleted=1 行、WAL 里未落盘的事务）。

**推荐：`bj-1` 就是现在的库，一个字节都不改。**

| 片 | 怎么来 | 迁移成本 | 风险 |
| --- | --- | --- | --- |
| `bj-1` | **`data/osm/osm.sqlite` 原样**（或它的 `VACUUM INTO` 快照） | **零** | **零**。它与今天逐字节相同 ⇒ 判据 2/3/4 在 `bj-1` 内自动成立 |
| `sjz-1` | 现成的 `data/osm/hebei-only.sqlite`（110,766 节点 / 16,037 way / 311 关系） | 零（文件挪个位置 + 改注册表） | 低。**但要注意**：它与 `bj-1` 共有全部 110,766 个 id（实测），这是"同 id 出现在两片"的**第一个真实案例** ⇒ 必须验证 4.2 的去重（尤其 `deleted` 状态与 `version`） |
| `lf` / `tj` / `bd` / … | 新下载 + 新导入（`tools/import-osm.js` 或 `tools/fetch-overpass.js --bbox` 后导入） | 每个城市一次导入 | 低（新库，无存量数据） |

**代价（如实说）**：`bj-1` 里其实**装着北京 + 石家庄**（2,182,456 节点），
所以它不是"纯北京片"，`sjz-1` 里的数据在 `bj-1` 中**重复存在**。
这有两个后果：
1. `bj-1` 的查询成本与今天**完全相同**（这正是我们想要的：H2 自动成立）；
2. **`sjz-1` 的每一行都必须与 `bj-1` 保持一致**，否则就是分叉。
   → 要么**在 P2 之前把石家庄从 `bj-1` 里删掉**（`DELETE FROM nodes WHERE id IN (SELECT id FROM sjz-1)`，
   这是一次**破坏性操作**，必须先备份 + 先验证 `sjz-1` 完整），
   要么**让 `sjz-1` 只读且不参与写入路由**（写入一律落 `bj-1`，`sjz-1` 当"只读的邻近片"）。

**推荐**：P1 阶段就让 `sjz-1` **只读**（`owner.sqlite` 里石家庄元素的属主仍是 `bj-1`），
这样"同 id 两片"在 P1 是**纯读**问题（用 4.2 的"同版本取属主片"就解决了），
不会产生分叉。等 P2 的写入路由稳定之后，再做一次显式的"石家庄元素搬家"。

### 11.2b 裁片时"互斥性"由谁保证

**由人定的声明矩形保证，不要求两片的内容不相交。** 这与 §3.6 的两级判定是自洽的：

- **声明矩形互斥** ⇒ 路由能唯一确定"该查哪几片"，不会因为两片都覆盖同一块而重复下发；
- **内容重叠** ⇒ 由 §4.2 的去重 + §5.8 的属主/镜像规则处理；
- **绝不要**为了"让两片的内容不重叠"去删元素（那是不可逆操作，且会破坏提取包的完整性）。

实测的反面教材就是 `beijing` × `hebei`：**声明矩形相交、内容还是严格包含**，
所以它只能按 §5.8 的"镜像片"处理，或者干脆重新裁片（§5.8.4）。
